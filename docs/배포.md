# 프론트 배포 (S3 + CloudFront)

프론트 빌드(`dist/`)를 S3에 올리고 CloudFront 한 도메인으로 내보내는 절차다. **처음 한 번 만드는 것**(2~3장)과 **배포할 때마다 하는 것**(5장)으로 나뉜다.
보안 점검 항목은 `docs/보안명세서.md` 9장이 원본이고, 여기는 그 순서대로 콘솔에서 무엇을 누르는지를 적는다.
2026-10-08부터는 **main 에 합치면 GitHub Actions가 자동으로 배포한다**(9장 — 처음 한 번 설정). 5장은 그것이 안 될 때 손으로 하는 길이다.

- 백엔드(서울 리전 EC2 한 대 · RDS · ElastiCache for Valkey, **ALB 없음**)는 이 문서 밖이다. `/api/*` 동작만 3.6에서 같은 배포에 붙이는 법을 적는다
- 콘솔 화면은 가끔 바뀐다. 버튼 이름이 이 문서와 다르면 **같은 뜻의 항목**을 찾고, 확신이 없으면 그 자리에서 멈추고 물어본다
- ⛔ **액세스 키 · 시크릿은 누구에게도(채팅 포함) 보내지 않는다.** `aws configure` 로 내 컴퓨터에만 저장한다

---

## 0. 한눈에

```
                         CloudFront 배포(프론트 · API 공용, dxxxx.cloudfront.net)
                                        |
             +--------------------------+--------------------------+
             |                                                     |
   /api/*  (3.6, 백엔드 준비 뒤)                        기본 동작 /*  (3.4 · 3.5)
   → EC2:8080 (HTTP, CloudFront에서만 열림)            → 프론트 S3 버킷(OAC, 퍼블릭 차단)
   캐시 끔 · 함수 없음                                   viewer-request 함수 spa-rewrite
                                                        응답 헤더 정책 lost-and-found-front-security
```

- **SPA 주소(`/posts/3` 새로고침 · 공유 링크)는 CloudFront Function이 받는다** — `deploy/cloudfront/spa-rewrite.js`. 기본 동작 하나에만 붙인다
- ⛔ **"오류 페이지(커스텀 오류 응답) 403/404 → `/index.html`"은 만들지 않는다.** 이 설정은 동작별이 아니라 **배포 전체**에 걸려서 `/api/*`의 403 `FORBIDDEN_ACCESS` · 404 `POST_NOT_FOUND`까지 200 HTML로 바뀐다. 프론트가 `code`로 나누는 동작(없는 글 · 권한 없음 · 재발급)이 전부 깨진다
- 사진은 **다른 버킷**(`lostfound-images-solmin-seoul`)이고 **다른 CloudFront 배포**로 내보낸다. 같은 배포에 붙이면 사진 키가 `posts/…`로 시작해 `/posts/*` 동작이 앱 주소 `/posts/3`과 부딪친다. 그 도메인(`https://d1xmzetvs0f1oh.cloudfront.net`, 2026-10-06 생성 · OAC)이 빌드의 `CSP_IMAGE_ORIGINS`가 된다(보안명세서 4장)

## 1. 비용 먼저

만들기 전에 읽는다. **금액은 여기에 적지 않는다** — 계정 요금 모델(12개월 프리 티어 / 크레딧)과 시점에 따라 다르고, 틀린 숫자가 가장 위험하다. 확인 경로를 따라가 직접 본다.

| 항목 | 과금 방식 | 언제 생기나 |
|---|---|---|
| S3 프론트 버킷 | **사용량** — 저장 용량 + 요청 수(업로드 PUT · CloudFront가 가져가는 GET) | 버킷을 만드는 것만으로는 없다. 파일을 올리면 생긴다(빌드는 수 MB · 100여 개 파일) |
| CloudFront 배포 | **사용량** — 내보낸 데이터 양 + 요청 수. 배포를 만들 때 **요금제를 고르는 화면**이 나올 수 있다(아래) | 요청이 들어올 때 |
| CloudFront Functions | **실행 횟수** — 기본 동작으로 오는 요청마다 1번 돈다(사진 · API 요청은 이 함수를 타지 않는다) | 요청이 들어올 때 |
| 캐시 무효화 | **경로 개수** — 매달 일정 개수까지 무료, 넘으면 경로당. 스크립트는 한 번에 3개(`/index.html` · `/theme-init.js` · `/favicon.svg`)만 보낸다 | 배포할 때마다 |
| OAC · 응답 헤더 정책 · 캐시 정책 | 만드는 것 자체에는 요금 항목이 없다 | — |
| WAF(보안 보호) | **켜면 월 요금 + 요청 수**. 이 문서에서는 켜지 않는다 | 배포 생성 화면에서 켤 때 |
| CloudShell(3.3에서 사용) | 콘솔 안의 명령줄. 추가 요금이 없다고 안내돼 있다 — 화면 안내를 한 번 확인 | — |
| 자동 배포(9장) — IAM ID 제공업체 · 역할 · GitHub Actions | 요금 항목이 없다 · 공개 리포는 무료로 안내돼 있다(확인 경로는 9.1) | — |

**확인 경로**
- 무료 범위 · 남은 크레딧 : 콘솔 오른쪽 위 **계정 이름** → **결제 및 비용 관리** → 왼쪽 **프리 티어** / **크레딧**
- 서비스별 단가 : 브라우저에서 `aws.amazon.com/cloudfront/pricing` · `aws.amazon.com/s3/pricing` (서울 = 아시아 태평양(서울))
- 실제로 쓴 금액 : **결제 및 비용 관리** → 왼쪽 **청구서**(서비스별로 펼친다). 예산 알림(제로 지출)이 이미 걸려 있다 — 메일이 오면 멈추고 본다
- **CloudFront 요금제 화면이 나오면** : 정액 요금제와 사용량 요금(Pay as you go) 중에 고르라는 화면일 수 있다. 각 요금제에 **무엇이 포함되고, 한도를 넘으면 어떻게 되는지(추가 요금 / 속도 제한)**를 그 화면에서 읽는다. 모르겠으면 **고르지 말고 멈춘다**

## 2. 준비 (내 컴퓨터, 한 번만)

### 2.1 AWS CLI

1. PowerShell에서 `winget install Amazon.AWSCLI` → 새 터미널을 열고 `aws --version` 이 `aws-cli/2.…` 를 찍는지 본다
2. 배포 스크립트는 **Git Bash**에서 돌린다(`bash deploy/s3-upload.sh`). PowerShell에서는 안 된다

### 2.2 배포 전용 IAM 사용자

백엔드 앱이 쓰는 `lostfound-app` 키를 재사용하지 않는다(사진 버킷 권한만 있어야 한다). 배포만 하는 사용자를 따로 만든다.
**프론트 버킷(3.1)과 배포 ID(3.4)가 정해진 뒤에** 한다 — 정책에 둘 다 들어간다.

1. 콘솔 상단 검색창 **IAM** → **IAM** → 왼쪽 **정책** → **정책 생성** → 오른쪽 위 **JSON** → 아래를 붙여 넣고 `<…>`를 **모두** 바꾼다(버킷 이름 네 곳 · 계정 ID · 배포 ID)

   ```json
   {
     "Version": "2012-10-17",
     "Statement": [
       { "Sid": "FrontBucketList", "Effect": "Allow", "Action": "s3:ListBucket",
         "Resource": "arn:aws:s3:::<프론트 버킷 이름>" },
       { "Sid": "FrontUpload", "Effect": "Allow", "Action": "s3:PutObject",
         "Resource": "arn:aws:s3:::<프론트 버킷 이름>/*" },
       { "Sid": "FrontReadIndex", "Effect": "Allow", "Action": "s3:GetObject",
         "Resource": "arn:aws:s3:::<프론트 버킷 이름>/index.html" },
       { "Sid": "FrontPruneAssets", "Effect": "Allow", "Action": "s3:DeleteObject",
         "Resource": "arn:aws:s3:::<프론트 버킷 이름>/assets/*" },
       { "Sid": "Invalidate", "Effect": "Allow", "Action": ["cloudfront:CreateInvalidation", "cloudfront:GetInvalidation"],
         "Resource": "arn:aws:cloudfront::<계정 ID 12자리>:distribution/<배포 ID>" }
     ]
   }
   ```

   계정 ID는 콘솔 오른쪽 위 계정 이름을 누르면 보인다. **다음** → 이름 `lostfound-front-deploy` → **정책 생성**

   | 권한 | 범위 | 스크립트에서 쓰는 곳 |
   |---|---|---|
   | `s3:PutObject` | 버킷 전체(`/*`) | 업로드 — `assets/*` 와 `index.html` · `public/`의 해시 없는 파일(파일을 더하면 이름이 늘어난다) |
   | `s3:GetObject` | `index.html` 하나 | `prune` — 배포된 `index.html`을 받아 `dist/`와 비교 · 날짜 조회(`head-object`도 이 권한이다) |
   | `s3:DeleteObject` | **`assets/*`만** | `prune` — 옛 해시 청크만 지운다. 스크립트도 `assets/` 아래 평범한 이름이 아니면 멈춘다. 이 키로는 `index.html`을 지울 수 없다 |
   | `s3:ListBucket` | 버킷 | `prune` — `assets/` 목록 |
   | CloudFront 무효화 | 이 배포 하나 | 업로드 끝 — 해시 없는 파일 무효화 |

   자격 확인(`aws sts get-caller-identity`)은 권한이 필요 없다. 권한이 모자라면 AWS가 `AccessDenied`로 멈추고 스크립트는 그 자리에서 끝난다(지우는 것은 조회가 모두 된 뒤에만)
2. 왼쪽 **사용자** → **사용자 생성** → 이름 `lostfound-front-deployer` → "AWS Management Console에 대한 사용자 액세스 권한 제공"은 **체크하지 않는다** → **다음** → **직접 정책 연결** → `lostfound-front-deploy` 체크 → **다음** → **사용자 생성**
3. 만든 사용자 → **보안 자격 증명** 탭 → **액세스 키 만들기** → **명령줄 인터페이스(CLI)** → 확인 체크 → **다음** → **액세스 키 만들기**. 시크릿은 **이 화면에서 한 번만** 보인다
4. Git Bash에서 `aws configure --profile lostfound-deploy` → 키 · 시크릿을 **직접 입력**(채팅에 붙여 넣지 않는다), 리전 `ap-northeast-2`, 출력 `json`
5. `AWS_PROFILE=lostfound-deploy aws sts get-caller-identity` → `Arn`이 `…:user/lostfound-front-deployer`로 끝나는지 본다.
   업로드 스크립트도 매번 이것을 먼저 찍고, **이 사용자가 아니면 `--apply`를 멈춘다**(기본 프로필의 다른 키로 잘못 올리지 않게). 사용자 이름을 다르게 만들었으면 `DEPLOY_IAM_USER=<그 이름>`을 같이 준다. 우회 플래그는 없다

## 3. 콘솔에서 한 번만 만드는 것

오른쪽 위 리전이 **아시아 태평양(서울) ap-northeast-2** 인지 먼저 본다. 시드니(ap-southeast-2)와 헷갈리기 쉽다(9/28 사진 버킷 사건). CloudFront는 리전이 없는 서비스라 "글로벌"로 보여도 정상이다.

### 3.1 프론트 버킷

1. 상단 검색창 **S3** → **S3** → 왼쪽 **범용 버킷** → **버킷 만들기**
2. 버킷 이름 예 : `lostfound-front-solmin-seoul`(전 세계에서 유일해야 한다). **사진 버킷과 다른 버킷**이다 — 업로드 스크립트는 사진 버킷 이름을 넣으면 멈춘다
3. 객체 소유권 **ACL 비활성화됨**(기본) · **모든 퍼블릭 액세스 차단 — 체크 유지** · 버전 관리 **비활성화**(기본) · 암호화 기본값 → **버킷 만들기**
4. **정적 웹 사이트 호스팅은 켜지 않는다.** OAC는 일반 S3 주소로만 붙고, 퍼블릭을 열 이유도 없다

### 3.2 CloudFront Function — `spa-rewrite`

1. 상단 검색창 **CloudFront** → **CloudFront** → 왼쪽 **함수** → **함수 생성**
2. 이름 `spa-rewrite` · 런타임 **cloudfront-js-2.0** → **함수 생성**
3. **빌드** 탭의 코드를 전부 지우고 `deploy/cloudfront/spa-rewrite.js` 내용을 **통째로** 붙여 넣는다 → **변경 사항 저장**
4. **테스트** 탭 → 이벤트 유형 **뷰어 요청** · URL 경로 `/posts/3` → **함수 테스트** → 출력의 `uri`가 `/index.html` 인지 본다.
   `/assets/index-abc.js` · `/api/posts` 로 한 번씩 더 — 둘 다 **그대로** 나와야 한다
5. **게시** 탭 → **함수 게시**. 게시하지 않으면 배포에 연결할 수 없다(연결되는 것은 게시본 LIVE다)

함수를 고치면 리포 파일을 먼저 고치고 `npm test`(`spa-rewrite.test.ts`)를 돌린 뒤, 3~5를 다시 한다.

### 3.3 응답 헤더 정책 — `lost-and-found-front-security`

1. 리포의 `docs/cloudfront-response-headers-policy.json` CSP `img-src`가 **사진 CloudFront 도메인**(`https://d1xmzetvs0f1oh.cloudfront.net`)인지 본다(2026-10-06에 바꿔 두었다). 사진 도메인이 바뀌면 이 JSON · `build/csp.ts`의 `DEFAULT_IMAGE_ORIGINS` · `deploy/s3-upload.sh`의 `PHOTO_ORIGIN`을 같이 바꾼다 → `npm test` 통과(보안명세서 9.1)
2. 콘솔 위쪽 막대의 **CloudShell** 아이콘(`>_`)을 누른다 → 열리면 오른쪽 위 **작업** → **파일 업로드** → 그 JSON 파일
3. CloudShell에서

   ```bash
   aws cloudfront create-response-headers-policy \
     --response-headers-policy-config file://cloudfront-response-headers-policy.json
   ```

4. 왼쪽 **정책** → **응답 헤더** 탭에 `lost-and-found-front-security`가 보이면 된다(3.5에서 고른다)

### 3.4 배포(distribution) 만들기 + OAC

1. 왼쪽 **배포** → **배포 생성**. 요금제 화면이 나오면 1장 끝을 읽고 고른다
2. 원본(Origin) : **Amazon S3** → 3.1의 버킷 선택(`…s3.ap-northeast-2.amazonaws.com`, 웹 사이트 주소가 아니다)
3. 원본 액세스 : **원본 액세스 제어 설정(권장)** → 없으면 **제어 설정 생성**(서명 요청 · 기본값) → 선택.
   "S3 버킷에 비공개 접근 허용" 같은 자동 설정 체크가 보이면 켠다(버킷 정책을 대신 넣어 준다)
4. 웹 애플리케이션 방화벽(WAF) : **보안 보호 활성화하지 않음**(1장 — 켜면 요금)
5. 기본 루트 객체 : `index.html`(함수가 `/`도 바꾸지만 함수를 떼었을 때를 위해 둔다)
6. 나머지 기본 동작 항목은 3.5에서 한 번에 고친다 → **배포 생성**
7. 만든 뒤 위쪽에 **"S3 버킷 정책을 업데이트해야 합니다"** 안내가 뜨면 **정책 복사** → S3 → 프론트 버킷 → **권한** 탭 → **버킷 정책** → **편집** → 붙여 넣기 → **변경 사항 저장**.
   정책은 `cloudfront.amazonaws.com`에 `s3:GetObject`만 주고 `AWS:SourceArn`이 이 배포일 때만이다. **퍼블릭 액세스 차단은 켠 그대로 둔다**
8. 배포 목록의 **ID**(`E…`)와 **배포 도메인 이름**(`dxxxx.cloudfront.net`)을 적어 둔다. 상태가 **배포 중** → 날짜로 바뀌면 끝(몇 분)

`s3:ListBucket`을 CloudFront에 주지 않으므로 **없는 파일은 S3가 403을 준다**(404가 아니다). 정상이다 — 없는 청크가 HTML로 덮이지 않는다는 뜻이다.

### 3.5 기본 동작(`/*`) 설정

배포 → **동작** 탭 → **기본값(\*)** 체크 → **편집**

| 항목 | 값 | 이유 |
|---|---|---|
| 뷰어 프로토콜 정책 | **Redirect HTTP to HTTPS** | 보안명세서 9.3 |
| 허용된 HTTP 방법 | **GET, HEAD** | 정적 파일만 |
| 캐시 키 및 원본 요청 | **캐시 정책** → `CachingOptimized`(관리형) | S3가 붙인 `Cache-Control`(4장)을 따른다 |
| 응답 헤더 정책 | `lost-and-found-front-security` | 3.3 |
| 함수 연결 → 뷰어 요청 | 함수 유형 **CloudFront Functions** · 함수 `spa-rewrite` | 3.2. 뷰어 응답 · 원본 요청 · 원본 응답은 비운다 |

**변경 사항 저장**. 배포 → **오류 페이지** 탭은 **비어 있어야 한다**(0장).

**최소 TLS 버전은 지금은 고르지 않는다(고를 수 없다).** 기본 인증서(`*.cloudfront.net`)를 쓰는 동안에는 배포 **설정** → **보안 정책**을 바꿀 수 없다 — CloudFront가 정해 둔 값이 쓰인다.
최소 TLS 1.2는 **사용자 도메인 + ACM 인증서**(CloudFront용 인증서는 **버지니아 북부 us-east-1**에서 발급)를 붙인 뒤에 보안 정책을 `TLSv1.2_2021` 이상으로 고른다(보안명세서 9.3). 그 전까지 HTTPS 강제는 위의 **Redirect HTTP to HTTPS**와 응답 헤더 정책의 HSTS가 맡는다

### 3.6 `/api/*` 동작 — 백엔드 EC2

ALB는 쓰지 않는다(서버가 한 대라 비용만 든다). CloudFront가 `/api/*`를 **EC2의 8080으로 바로** 넘긴다. 시작 전에 백엔드 쪽이 이렇게 돼 있는지 본다(이 문서 밖)

- EC2에 **탄력적 IP**가 붙어 있다 — 원본 도메인(퍼블릭 IPv4 DNS)이 이 IP에서 나온다. IP가 바뀌면 원본 도메인도 바뀐다
- EC2 보안 그룹 인바운드의 8080은 소스가 AWS 관리형 접두사 목록 **`com.amazonaws.global.cloudfront.origin-facing`** 하나뿐이다(`0.0.0.0/0`이 아니다)
- 백엔드 컨테이너가 8080으로 떠 있다

1. 원본 도메인 찾기 : 상단 검색창 **EC2** → **EC2** → 왼쪽 **인스턴스** → 백엔드 인스턴스 체크 → 아래 **세부 정보** 탭 → **퍼블릭 IPv4 DNS**(`ec2-…ap-northeast-2.compute.amazonaws.com`) 옆 복사 아이콘.
   IP 숫자(`3.xx.xx.xx`)가 아니라 이 이름을 쓴다 — CloudFront 원본에는 IP를 넣을 수 없다
2. **CloudFront** → 배포 → **원본** 탭 → **원본 생성**

   | 항목 | 값 | 이유 |
   |---|---|---|
   | 원본 도메인 | 1에서 복사한 퍼블릭 IPv4 DNS를 **붙여 넣는다** | 목록에는 S3 · 로드 밸런서만 뜬다. EC2는 고르지 않고 직접 넣는다 |
   | 프로토콜 | **HTTP만** | 아래 "왜 HTTP인가" |
   | HTTP 포트 | **8080** | 백엔드 컨테이너 포트. 기본값 80을 꼭 바꾼다 |
   | 원본 경로 | **비운다** | `/api`를 넣으면 `/api/api/…`로 간다 |
   | 이름 | `lostfound-api-ec2` | 동작에서 고를 때 알아보기 쉽게 |
   | 사용자 정의 헤더 추가 · Origin Shield | 넣지 않음 · **아니요** | Origin Shield는 켜면 요금 |

   → **원본 생성**
3. **동작** 탭 → **동작 생성** → 경로 패턴 `/api/*` · 원본 = `lostfound-api-ec2` · 뷰어 프로토콜 정책 **Redirect HTTP to HTTPS**(기본 동작과 같다)
4. 허용된 HTTP 방법 **GET, HEAD, OPTIONS, PUT, POST, PATCH, DELETE** · 캐시 정책 `CachingDisabled` · 원본 요청 정책 `AllViewerExceptHostHeader`(쿠키 · 쿼리 · 헤더를 넘긴다 — 재발급 쿠키가 여기 실린다)
5. **함수 연결은 비운다.** 응답 헤더 정책은 프론트 정책이 아니라 가벼운 것(보안명세서 4장 끝, 백엔드 담당) → **동작 생성**
6. 동작 목록에서 `/api/*`가 **기본값(\*)보다 위**(우선순위 숫자가 작음)인지 본다

**왜 HTTP인가** — CloudFront → EC2 구간만 HTTP다. 브라우저 → CloudFront는 그대로 HTTPS다.

- 원본을 HTTPS로 받으려면 EC2가 공인 인증서를 내밀어야 하는데, 사용자 도메인 · 인증서가 아직 없다(`…compute.amazonaws.com` 이름으로는 인증서를 받을 수 없다)
- 그 대신 보안 그룹이 8080을 **CloudFront 접두사 목록에서만** 연다. 인터넷에서 `EC2:8080`으로 바로 오는 요청은 닿지 않는다 — 보안 그룹을 `0.0.0.0/0`으로 넓혀 문제를 풀지 않는다
- 이 목록에는 다른 계정의 CloudFront도 들어 있다. 우리 배포만 받게 하려면 원본 사용자 정의 헤더 비밀값을 백엔드가 확인해야 한다(백엔드 개선안 — 지금은 하지 않는다)
- 사용자 도메인 + ACM 인증서를 붙이면(3.5 끝) 이 구간도 HTTPS로 올린다

**백엔드 CORS 허용 출처를 사이트 도메인으로** — `AllViewerExceptHostHeader`는 Host를 넘기지 않아서 백엔드가 받는 Host는 EC2 주소다.
브라우저가 POST · PUT · DELETE에 붙이는 `Origin: https://<사이트 CloudFront 도메인>`과 달라 백엔드가 이것을 **다른 출처 요청**으로 보고, 허용 목록에 없으면 403(`Invalid CORS request`)으로 막는다 — 목록(GET)은 되는데 **로그인부터 안 된다.**

1. 백엔드 환경변수 `CORS_ALLOWEDORIGINS=https://<사이트 CloudFront 도메인>`(0장의 `dxxxx.cloudfront.net`, 끝에 `/` 없이)
2. 백엔드 컨테이너를 **다시 만든다**(지우고 새로 실행). 재시작만으로는 환경변수가 바뀌지 않는다
3. 6장의 `/api` 확인을 한다

## 4. 캐시 전략

`Cache-Control`은 **업로드할 때 S3 객체에 붙인다**(스크립트가 한다). CloudFront(`CachingOptimized`)와 브라우저가 이 값을 따른다.

| 파일 | `Cache-Control` | 이유 |
|---|---|---|
| `/assets/*` (JS · CSS · 글꼴 조각) | `public, max-age=31536000, immutable` | 이름에 내용 해시가 있다(`index-D4f_x-9Q.js`). 내용이 바뀌면 이름이 바뀌니 1년 두어도 옛것을 받을 일이 없다 |
| `index.html` | `no-cache` | 매번 확인한다(바뀌지 않았으면 304라 가볍다). 새 배포가 곧바로 보인다 |
| `theme-init.js` · `favicon.svg` (`public/`의 해시 없는 파일) | `no-cache` | 이름이 고정이라 길게 캐시하면 고친 뒤에도 옛것이 남는다. `theme-init.js`는 `index.html`이 동기로 부르는 작은 파일이다 |

- 해시 없는 파일은 CloudFront 엣지에도 캐시 정책의 최소 TTL만큼 남을 수 있어서, 올린 뒤 그 파일들만 **무효화**한다(`/index.html` · `/theme-init.js` · `/favicon.svg`). `/assets/*`는 무효화하지 않는다 — 이름이 새로우니 필요 없다
- 앱 주소(`/posts/3`)는 함수가 `/index.html`로 바꾼 **뒤에** 캐시를 찾으므로 `/index.html` 하나만 비우면 모든 주소가 새것이 된다
- `public/`에 파일을 더하면 스크립트가 알아서 `no-cache`로 올리고 무효화 목록에 넣는다. 모르는 확장자면 멈춘다(`content_type`에 더한다)

## 5. 배포할 때마다

> 자동 배포(9장)를 설정한 뒤에는 이 장이 **자동 배포가 안 될 때의 비상 경로**다. 옛 청크 정리(`prune`, 아래)는 자동으로 하지 않으니 계속 여기서 한다.

Git Bash, 리포 맨 위(`C:\Users\solmi\Downloads\Front`)에서.

```bash
git switch main && git pull
npm ci
CSP_IMAGE_ORIGINS=https://d1xmzetvs0f1oh.cloudfront.net npm run build   # 사진 CloudFront. 보안명세서 9.2 확인 항목을 본다

export AWS_PROFILE=lostfound-deploy FRONT_BUCKET=<프론트 버킷> DISTRIBUTION_ID=<E…>
bash deploy/s3-upload.sh            # 미리보기 — 올릴 파일 · Content-Type · 캐시 값만 찍는다
bash deploy/s3-upload.sh --apply    # 실제로 올리고 무효화
```

스크립트(`deploy/s3-upload.sh`)가 하는 일

0. 자격 확인 — `aws sts get-caller-identity`의 ARN을 찍고, 배포 전용 사용자(`lostfound-front-deployer`, 2.2)가 아니면 `--apply`는 멈춘다. 미리보기는 경고만 하고 계속한다. 버킷 이름도 S3 이름 규칙(소문자 · 숫자 · 점 · 하이픈, 3~63자)에 맞는지 먼저 본다
1. 점검 — 빌드 결과에 CSP meta가 있는지, 사진 출처(`img-src`)에 사진 CloudFront(`PHOTO_ORIGIN`)가 있고 S3 주소 · `http://`(로컬 목 서버)가 없는지, 소스맵이 없는지, 모르는 확장자가 없는지. 하나라도 걸리면 **아무것도 올리지 않고** 멈춘다
2. `/assets/*` 먼저 올린다 — 확장자별 `Content-Type`을 직접 붙인다. 윈도우의 AWS CLI는 `.js`를 `text/plain`으로 올리는 일이 있고, `nosniff` 헤더 때문에 그러면 **화면이 하얗게 뜬다**
3. 해시 없는 파일 → **`index.html`은 맨 마지막.** 먼저 바뀌면 새 청크가 올라가기 전 틈에 새 `index.html`이 없는 파일을 부른다
4. 해시 없는 파일만 무효화

### 옛 청크는 바로 지우지 않는다

`aws s3 sync --delete`를 쓰지 않는다. 배포하는 순간 이미 옛 `index.html`을 받아 둔 탭(열어 둔 채 둔 탭)은 화면을 옮길 때 **옛 청크**(`PostEditPage-옛해시.js`)를 부른다. 그 파일을 지웠으면 그 화면이 뜨지 않는다(7장).
그래서 업로드는 더하기만 하고, 정리는 **따로 가끔** 한다.

```bash
bash deploy/s3-upload.sh prune            # 미리보기
bash deploy/s3-upload.sh prune --apply    # 지운다
```

- **지금 배포가 7일을 넘긴 뒤에만** 지운다(`PRUNE_DAYS=14` 처럼 바꿀 수 있다). 기준은 배포된 `index.html`이 마지막으로 올라간 날짜다. 7일이 안 됐으면 아무것도 지우지 않고 언제부터 되는지 알려 준다
  - 까닭 : 옛 빌드의 `index.html`은 **지금 배포가 올라가기 전에만** 받을 수 있었다. 지금 배포가 7일을 넘기면 옛 청크를 부를 탭은 그 전에 열어 **7일 넘게 새로고침하지 않은 탭**뿐이다
  - 파일마다 날짜만 보면 틀린다 — 빌드 A(0일) → B(10일) 바로 뒤에 정리하면 A의 청크는 10일 묵었어도, 9일에 A를 받은 탭이 아직 그것을 부른다(2026-09-29까지 스크립트가 이랬다)
  - 같은 빌드를 다시 올려도(`--apply`) `index.html` 날짜가 새로워져 그날부터 다시 센다. 배포가 잦으면 정리가 계속 미뤄지는데, 그래도 된다(아래)
- 지우는 것 : 그중에서도 `assets/` 가운데 **지금 빌드에 없고** 7일 넘게 다시 올라가지 않은 파일
- **배포된 `index.html`이 지금 `dist/`와 같을 때만** 돈다. 배포하지 않은 새 빌드로 정리하면 살아 있는 청크를 지우게 되어 막아 두었다
- 조회(`index.html` 받기 · 날짜 · 목록)가 하나라도 실패하거나, 날짜 · 이름 모양이 낯설면 **아무것도 지우지 않고** 멈춘다. 지우는 것은 `assets/` 아래뿐이다(IAM도 `assets/*`만 지울 수 있다, 2.2)
- 안 해도 망가지지 않는다. 쌓이는 것은 저장 용량(수 MB 단위)뿐이다 — 한 달에 한 번이면 충분하다

### 되돌리기

옛 커밋으로 돌아가 같은 절차를 다시 한다(`git switch --detach <커밋>` → `npm ci` → 빌드 → `--apply` → `git switch main`). 옛 청크를 지우지 않았으니 파일이 모자라지 않는다.

## 6. 확인

무효화가 **완료됨**이 된 뒤(배포 → **무효화** 탭). 윈도우에도 `curl`이 있다.

```bash
D=https://dxxxx.cloudfront.net
curl -sI $D/posts/3            | grep -iE "^HTTP|content-type|cache-control"   # 200 · text/html · no-cache
curl -sI $D/assets/nope-0000.js | grep -iE "^HTTP"                             # 403 (200 HTML이면 잘못 — 오류 페이지 탭 확인)
curl -sI "$D/?keyword=%EC%A7%80%EA%B0%91" | grep -iE "^HTTP"                  # 200
JS=$(curl -s $D/ | grep -o '/assets/index-[^"]*\.js' | head -1)
curl -sI $D$JS                 | grep -iE "content-type|cache-control"         # text/javascript · max-age=31536000, immutable
curl -sI $D/theme-init.js      | grep -iE "content-type|cache-control"         # text/javascript · no-cache
```

백엔드가 붙은 뒤에는(3.6)

```bash
curl -s $D/api/posts/999999999                                                   # JSON 404 POST_NOT_FOUND
curl -s -o /dev/null -w "%{http_code}\n" -X POST -H "Origin: $D" -H "Content-Type: application/json" \
  -d '{}' $D/api/auth/login                                                       # 400(입력 검증) — 403이면 CORS
```

- 첫 줄이 **JSON**(404 `POST_NOT_FOUND`)이어야 한다. HTML이 오면 오류 페이지가 걸려 있거나 `/api/*` 동작 순서가 틀렸다. 502 · 504면 8장
- 둘째 줄이 403이면 백엔드 CORS 허용 출처에 사이트 도메인이 없다(3.6 끝)

그다음 보안명세서 9.4(헤더 · CSP 위반 0건 · 화면 한 바퀴)를 한다. 브라우저에서는 `/posts/3`에서 **새로고침**을 한 번 해 본다.

## 7. 배포 중 열려 있던 탭 — 나눠 받는 화면

등록 · 수정 · 상세 · 설정 · 내가 쓴 글은 들어갈 때 코드를 받는다(`lazy`, `src/app/routes.tsx`). 옛 탭이 받으려는 청크가 없으면

- **이미 처리돼 있다** — 그 라우트의 `errorElement`(`src/app/RouteLoadError.tsx`)가 헤더는 그대로 두고 본문에 "화면을 불러오지 못했습니다. 연결을 확인하고 다시 시도해 주세요." + **[다시 시도]**(같은 주소로 새로고침)를 띄운다. 새로고침하면 새 `index.html` → 새 청크라 풀린다
- 없는 청크는 함수가 `index.html`로 덮지 않아(확장자가 있다) **403으로 분명히 실패**한다. HTML이 JS 자리에 오면 오류가 흐려지고 브라우저 캐시에도 남는다
- 옛 청크는 지금 배포가 7일을 넘긴 뒤에야 지우므로(5장) 이 화면을 보는 것은 **지금 배포 전에 열어 두고 7일 넘게 새로고침하지 않은 탭**뿐이다(`PRUNE_DAYS`를 바꾸면 그 날수)
- **자동 새로고침은 넣지 않았다.** 청크를 못 받는 흔한 까닭이 연결 끊김인데, 그때 자동으로 새로고침하면 앱 화면 대신 브라우저의 "인터넷 연결 없음" 화면이 뜬다. 한 번 누르는 버튼이 덜 거슬린다

## 8. 막힐 때

| 증상 | 먼저 볼 곳 |
|---|---|
| 화면이 하얗고 콘솔에 `MIME type ('text/plain')` | 파일을 콘솔 · 다른 명령으로 올렸다. `deploy/s3-upload.sh --apply`로 다시 올린다(형식을 직접 붙인다) |
| `/posts/3` 새로고침이 403 · `AccessDenied` XML | 함수를 **게시**하지 않았거나 기본 동작에 **뷰어 요청**으로 연결하지 않았다(3.2 · 3.5) |
| 모든 주소가 403 | 버킷 정책을 붙이지 않았다(3.4-7) · 원본이 웹 사이트 주소다 |
| `/api/…` 응답이 HTML | 오류 페이지 탭에 무언가 있다(지운다) · `/api/*` 동작이 없거나 기본값보다 아래 |
| `/api/…`가 502 · 504 (CloudFront 오류 화면) | 원본 EC2에서 응답을 받지 못했다(3.6). **504**(시간 초과)면 보안 그룹 8080 인바운드에 `com.amazonaws.global.cloudfront.origin-facing`이 없다 · 인스턴스가 꺼졌다 · 원본 HTTP 포트가 8080이 아니다(보안 그룹이 다른 포트를 막는다) · 원본 도메인이 옛 퍼블릭 IPv4 DNS다(탄력적 IP를 바꿨으면 다시 복사). **502**면 백엔드 컨테이너가 꺼졌다(EC2에서 `docker ps`) · 원본 프로토콜이 HTTPS다(8080은 HTTP만 받는다) |
| 목록은 되는데 로그인 · 등록(POST)이 403 `Invalid CORS request` | 백엔드 `CORS_ALLOWEDORIGINS`가 사이트 도메인이 아니다(끝 `/` · http 주의) · 바꾼 뒤 컨테이너를 다시 만들지 않았다(3.6 끝) |
| 무효화 경로가 `C:/Program Files/Git/index.html` | Git Bash가 `/`로 시작하는 인자를 바꿨다. 스크립트는 `MSYS_NO_PATHCONV=1`로 막는다 — 직접 명령을 칠 때도 앞에 붙인다 |
| 사진만 안 보이고 콘솔에 CSP `img-src` 위반 | `CSP_IMAGE_ORIGINS`와 응답 헤더 JSON의 `img-src`가 사진 도메인과 다르다(보안명세서 4장 — 둘의 교집합이 걸린다) |
| 새 배포가 안 보인다 | 무효화가 완료됐는지(6장) · 브라우저 강력 새로고침(Ctrl+Shift+R) |
| `[중단] 배포 전용 사용자(…)가 아닙니다` | `AWS_PROFILE`이 비었거나 다른 프로필이다. `export AWS_PROFILE=lostfound-deploy`(2.2). 찍힌 ARN이 맞는 사람인데 이름만 다르면 `DEPLOY_IAM_USER` |
| `prune`이 `정리하지 않습니다`만 찍는다 | 정상이다. 지금 배포가 `PRUNE_DAYS`일(기본 7)을 넘기지 않았다. 찍힌 날짜 뒤에 다시 돌린다(5장) |
| GitHub **Actions** 탭의 **Deploy**가 빨갛다 | 9.6 |

## 9. 자동 배포 (GitHub Actions)

**배포는 main 에서만 한다 — main 이 곧 배포용 브랜치다.** 작업은 다른 브랜치에서 하고, main 에 합치는(push) 순간 CI → 배포가 이어서 돈다.

워크플로는 `.github/workflows/deploy.yml`이다. 하는 일은 5장과 같다 — 같은 스크립트(`deploy/s3-upload.sh --apply`)가 같은 순서 · 캐시 · 무효화로 올린다. 다른 점은 권한을 **액세스 키가 아니라 OIDC 역할**로 받는다는 것이다. GitHub에 키를 넣지 않는다(기능명세서 11장).
처음 한 번 9.2 ~ 9.4를 하면 그다음부터는 할 일이 없다. 5장(손으로 배포)은 **자동 배포가 안 될 때의 비상 경로**로 남긴다.

```
main 에 push ─→ CI(ci.yml) 통과 ─→ Deploy(deploy.yml)
                                    설정 확인 → 체크아웃(CI가 통과한 바로 그 커밋) → npm ci → 빌드
                                    → AWS 역할 받기(OIDC, 15분짜리 임시 키) → s3-upload.sh --apply
                                    → 사이트의 index.html 이 이 빌드와 같은지 확인 → 요약 한 줄
```

### 9.0 main 에서만 — 세 겹

| 겹 | 어디서 | 막는 것 |
|---|---|---|
| ① 워크플로 조건 | `deploy.yml`의 `if` | 자동은 main 에 **push 된** 커밋의 CI 가 **성공**했을 때만 — PR · 포크 · 다른 브랜치의 CI 는 건너뛴다. 수동 실행(Run workflow)은 main 에서만 — 다른 브랜치에서 누르면 `main-only` 작업이 까닭을 남기고 실패한다 |
| ② GitHub 환경 `production` | 리포 Settings → Environments(9.4) | 배포 작업은 `production` 환경으로 돈다. 환경의 배포 브랜치가 `main` 하나라 다른 브랜치에서 돈 작업은 **시작 전에** 막힌다 — 누가 다른 브랜치에서 `deploy.yml`을 고쳐 ①을 지워도 |
| ③ IAM 역할 신뢰 정책 | AWS IAM 역할(9.3) | GitHub 토큰의 `sub`가 정확히 `repo:solmin6320@282091421/Lost-and-Found-Front@1380027425:environment:production`일 때만 역할을 넘겨준다(고정 ID 형식, 9.3). 다른 리포 · 포크 · 환경 없이 돈 작업(`…:ref:refs/heads/<브랜치>`)은 AWS가 거절한다 — ②를 피하려고 `environment`를 지워도 |

하나가 빠져도 나머지가 막는다. 셋 다 지킨다.

### 9.1 비용

**금액은 적지 않는다**(1장과 같은 까닭). 확인 경로를 따라가 직접 본다.

| 항목 | 과금 | 확인 |
|---|---|---|
| IAM ID 제공업체(OIDC) · IAM 역할 | 요금 항목이 없다 — IAM은 추가 요금 없이 제공된다고 안내돼 있다 | 브라우저에서 `aws.amazon.com/iam` 의 요금(Pricing) 안내 |
| 역할 받기(STS) | 요금 항목이 없다 | 같은 곳 |
| GitHub Actions | 공개 리포가 GitHub 호스팅 러너(`ubuntu-latest`)로 도는 것은 무료로 안내돼 있다 | GitHub 오른쪽 위 프로필 사진 → **Settings** → 왼쪽 **Billing and licensing**(화면에 따라 Billing and plans) · `docs.github.com`의 "About billing for GitHub Actions" |
| S3 업로드 · CloudFront 무효화 | 1장과 같다 — 손으로 올릴 때와 같은 양이 배포마다 든다. 배포가 잦으면 그만큼 는다 | 1장 확인 경로 |

### 9.2 AWS — GitHub를 ID 제공업체로 등록 (계정에 한 번)

AWS가 GitHub Actions가 내미는 토큰을 믿게 하는 설정이다. 나중에 백엔드 자동 배포도 이것을 같이 쓴다.

1. 상단 검색창 **IAM** → **IAM** → 왼쪽 **액세스 관리** 묶음의 **ID 제공업체** (IAM은 리전이 없다 — 오른쪽 위가 "글로벌"이어도 정상)
2. 목록에 `token.actions.githubusercontent.com`이 **이미 있으면 여기서 끝**이다. 같은 주소는 계정에 하나뿐이다(또 만들면 오류)
3. 오른쪽 위 주황 버튼 **제공업체 추가**(화면에 따라 '공급자 추가')
4. 제공업체 유형 **OpenID Connect**
5. 제공업체 URL `https://token.actions.githubusercontent.com` (끝에 `/` 없이)
6. 대상(Audience) `sts.amazonaws.com`
7. **지문 가져오기**(Get thumbprint) 버튼이 보이면 누른다. 요즘 화면에는 없을 수 있다 — 없으면 넘어간다
8. **제공업체 추가** → 목록에 `token.actions.githubusercontent.com`이 보이면 된다

### 9.3 AWS — 배포 역할 `lostfound-front-github-deploy`

권한은 2.2에서 만든 정책 **`lostfound-front-deploy`를 그대로** 붙인다(프론트 버킷 · 이 배포만). 손으로 올리는 사용자(`lostfound-front-deployer`)와 같은 권한을 GitHub는 키 없이 역할로 받는다.
정책이 아직 없으면 2.2-1대로 먼저 만든다.

1. IAM → 왼쪽 **액세스 관리** 묶음의 **역할** → **역할 생성**
2. 신뢰할 수 있는 엔터티 유형 **사용자 지정 신뢰 정책** → 아래 편집 칸의 내용을 전부 지우고 이 JSON 을 붙여 넣는다 → `<계정 ID 12자리>` **한 곳**을 바꾼다(콘솔 오른쪽 위 계정 이름을 누르면 보인다) → **다음**

   ```json
   {
     "Version": "2012-10-17",
     "Statement": [
       {
         "Sid": "GitHubDeployFromMainEnvironment",
         "Effect": "Allow",
         "Principal": {
           "Federated": "arn:aws:iam::<계정 ID 12자리>:oidc-provider/token.actions.githubusercontent.com"
         },
         "Action": "sts:AssumeRoleWithWebIdentity",
         "Condition": {
           "StringEquals": {
             "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
             "token.actions.githubusercontent.com:sub": "repo:solmin6320@282091421/Lost-and-Found-Front@1380027425:environment:production"
           }
         }
       }
     ]
   }
   ```

   - `aud` — AWS(STS)에 쓰라고 발급된 토큰인지
   - `sub` — **이 리포의 `production` 환경으로 돈 작업**인지(9.0 ③). 리포 이름 · 환경 이름이 한 글자라도 다르면 거절된다(대소문자도). 리포 이름을 바꾸면 여기도 바꾼다(지금 이름 `Lost-and-Found-Front`, 옛 이름 `Lost-and-Found---Front`가 아니다)
   - **고정 ID 형식**(2026-10-08 정정) — 이 리포는 GitHub OIDC 고정 ID 주체를 써서 `sub`가 `repo:<계정>/<리포>:…`가 아니라 `repo:<계정>@<번호>/<리포>@<번호>:…`다. 옛 모양으로 적으면 첫 배포가 `Not authorized to perform sts:AssumeRoleWithWebIdentity`로 멈춘다.
     `@` 뒤 숫자는 계정 · 리포의 고유 번호다 — 이름이 바뀌어도 그대로이고, 지우고 같은 이름으로 새로 만든 리포는 번호가 달라 통과하지 못한다.
     내 리포의 접두사는 브라우저로 `https://api.github.com/repos/solmin6320/Lost-and-Found-Front/actions/oidc/customization/sub`를 열면 `sub_claim_prefix`로 보인다(그 뒤에 `:environment:production`을 붙인 것이 `sub`)
   - 역할을 **이미 옛 값으로 만들었으면** : 역할 목록 → `lostfound-front-github-deploy` → **신뢰 관계** 탭 → **신뢰 정책 편집** → `sub` 줄의 값만 위 값으로 → **정책 업데이트**. 그다음 실패한 Deploy 실행에서 **Re-run jobs**
   - `StringEquals`(정확히 같을 때만)다. `StringLike` · `*`로 넓히지 않는다
   - 유형 가운데 **웹 자격 증명**도 있지만 조건을 화면이 대신 만든다. `sub`를 정확히 적으려고 직접 붙여 넣는다
3. 권한 추가 화면 → 검색창에 `lostfound-front-deploy` → 그 줄 **하나만** 체크 → **다음**
4. 역할 이름 `lostfound-front-github-deploy` · 설명 예 `GitHub Actions front deploy (OIDC)` → 아래 **1단계: 신뢰할 수 있는 엔터티 선택**에 붙여 넣은 JSON 이 그대로인지 · **2단계** 권한이 `lostfound-front-deploy` 하나인지 본다 → **역할 생성**
5. 역할 목록에서 `lostfound-front-github-deploy` → 위쪽 **요약**의 **ARN**(`arn:aws:iam::<12자리>:role/lostfound-front-github-deploy`) 옆 복사 아이콘. 9.4에서 붙여 넣는다
6. **최대 세션 지속 시간**은 기본(1시간) 그대로 둔다. 워크플로는 그보다 짧은 15분만 받는다

### 9.4 GitHub — 환경 `production` · 변수 넷

1. 브라우저에서 `github.com/solmin6320/Lost-and-Found-Front` → 위쪽 **Settings** → 왼쪽 **Environments**
2. **New environment** → Name `production`(소문자 — 9.3 신뢰 정책의 `environment:production`과 같아야 한다) → **Configure environment**.
   목록에 `production`이 **이미 있으면** 그것을 누른다. 변수를 넣기 전에 Deploy 가 한 번 돌면 GitHub이 같은 이름의 환경을 **제한 없이** 자동으로 만든다 — 그 환경에도 3을 꼭 한다
3. **Deployment branches and tags** → **No restriction**을 **Selected branches and tags**로 바꾼다 → **Add deployment branch or tag rule** → Ref type **Branch** · Name pattern `main` → **Add rule**. 목록에 `main` **하나만** 있어야 한다(9.0 ②)
4. **Required reviewers** · **Wait timer**는 켜지 않는다. 켜면 배포마다 승인을 눌러야 해서 자동 배포가 아니게 된다
5. 아래 **Environment variables** → **Add environment variable**을 네 번(Name · Value → **Add variable**). 바로 위의 **Environment secrets**가 아니다

   | Name | Value |
   |---|---|
   | `AWS_DEPLOY_ROLE_ARN` | 9.3-5에서 복사한 역할 ARN |
   | `FRONT_BUCKET` | 프론트 버킷 이름(3.1). 사진 버킷이 아니다 |
   | `CLOUDFRONT_DISTRIBUTION_ID` | **사이트** 배포의 ID(`E…`, 3.4-8). 사진 배포의 ID가 아니다 |
   | `SITE_URL` | `https://d3gltjya6f51ok.cloudfront.net` |

**Secrets 가 아니라 Variables 인 까닭** — 넷 다 비밀번호가 아니라 이름 · 주소다. 알아도 역할을 넘겨받을 수 없고(9.0 ③), Secrets 에 넣으면 로그에 `***`로 가려져 무엇이 틀렸는지 볼 수 없다.
공개 리포라 Actions 로그는 누구나 본다 — 계정 ID(ARN 안의 12자리) · 버킷 이름이 찍힌다. AWS는 계정 ID를 비밀번호처럼 다루지 않는다고 안내한다. 키 · 시크릿은 여전히 어디에도 넣지 않는다.

**처음 확인** — 다 넣었으면 리포 **Actions** → 왼쪽 **Deploy** → 오른쪽 **Run workflow** → Use workflow from **main** → **Run workflow**(9.5 수동). 초록이 되면 6장 확인을 한 번 한다.

### 9.5 흐름 — 자동 · 수동 · 되돌리기

- **자동** : main 에 push(PR 합치기 포함) → **CI** 통과 → **Deploy**가 그 커밋을 올린다. 리포 **Actions** 탭에서 본다. 실행 화면 아래 요약에 커밋 · 주소 · 결과가 한 줄로 남는다
  - CI 가 실패하거나 취소되면 Deploy 는 건너뛴다(목록에 회색 "skipped"). 앞 배포가 도는 중이면 뒤 배포는 기다린다(도중에 끊지 않는다)
- **수동** : **Actions** → 왼쪽 **Deploy** → 오른쪽 **Run workflow** → Use workflow from **main** → **Run workflow**.
  main 의 마지막 커밋을 **CI 결과를 보지 않고** 올린다 — 그 커밋의 CI 가 초록인지 먼저 본다. 설정을 처음 넣었을 때 · 변수를 고친 뒤에 쓴다
- **되돌리기**
  1. **git revert** — `git revert <커밋>` → main 에 push. 새 커밋으로 CI → Deploy 가 다시 돈다. main 의 기록과 사이트가 같아서 **이쪽이 기본**이다
  2. **이전 Deploy 다시 돌리기** — 급할 때. **Actions** → **Deploy** → 돌아갈 커밋의 **성공한** 실행 → 오른쪽 위 **Re-run jobs**(→ **Re-run all jobs**). 다시 돌려도 그 실행이 처음 받은 커밋(`head_sha`)을 그대로 올린다.
     GitHub은 처음 실행 뒤 **30일 안**의 실행만 다시 돌릴 수 있다. 다음에 main 에 push 하면 그 최신 커밋이 다시 올라가니, 고친 커밋을 올릴 때까지만 쓰는 방법이다
  3. 30일이 지났거나 Actions 가 안 되면 5장 **되돌리기**(손으로)
  - 옛 청크를 지우지 않으니(5장) 어느 쪽이든 파일이 모자라지 않는다
- **옛 청크 정리(`prune`)는 자동으로 하지 않는다** — 지금 배포가 7일을 넘긴 뒤에만 지울 수 있어 배포 직후에 돌면 늘 "정리하지 않습니다"로 끝나고, 지우는 일은 사람이 미리보기를 보고 하는 편이 안전하다. 한 달에 한 번 5장대로 손으로 한다.
  그래서 2.2의 사용자 · 프로필(`lostfound-deploy`)은 지우지 않는다(정리 · 비상 배포용)

### 9.6 실패했을 때

**Actions** → **Deploy** → 빨간 실행 → 빨간 단계를 펼친다. 변수를 고쳤으면 그 실행에서 **Re-run jobs**를 누르면 된다(변수는 다시 돌릴 때 새로 읽는다).

| 빨간 곳 · 메시지 | 까닭 · 할 일 |
|---|---|
| Deploy 가 목록에 아예 안 뜬다 | `deploy.yml`이 main 에 없다(자동 실행은 main 에 있는 파일로만 돈다) · CI 워크플로가 돌지 않았다(`ci.yml`의 `name: CI`를 바꿨으면 `deploy.yml`의 `workflows: [CI]`도) |
| **main 에서만 배포** 작업 — `배포는 main 에서만 합니다` | main 이 아닌 브랜치에서 Run workflow 를 눌렀다. Use workflow from 을 **main**으로 |
