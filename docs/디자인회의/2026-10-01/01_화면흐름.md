## 0. 핵심 과업 3개 — 지금 → 제안 후

측정 규칙 (390 · 로그인 · CSS px)
- **탭** : 앱 안에서 누르는 횟수. 글자 입력 · 기기 사진 고르기 창은 세지 않는다
- **손 스크롤** : 다음 조작에 닿으려고 손으로 내리는 거리. 읽으려고 내리는 거리는 세지 않는다. 스크린샷 좌표(전체 페이지 ÷ 2)에서 계산
- **선택지** : 결정하는 순간 한 화면에 함께 보이는 누를 것의 수(힉스)
- 제안 후 수치는 설계 추정이다. 구현 뒤 같은 도구(`meetshot/run.mjs`)로 다시 잰다

읽는 법 — **탭 수는 거의 그대로다.** 이 앱은 이미 탭이 짧다(가입 → 자동 로그인, 날짜 기본값 오늘, 유형 미리 고르기, 스크롤 복원). 줄어드는 것은 **거리(피츠)와 한 번에 보는 선택지(힉스)**, 그리고 "그 동작이 어디 있지"를 찾는 시간이다. 탭을 억지로 줄이려고 화면을 합치거나 확인을 빼는 제안은 하지 않았다.

### 화면 전환 점검 (본인 질문 "쓸데없는 화면 전환")

- **떠나지 않아도 되는데 옮기거나 덮는 곳**
  - 필터 — 카테고리 한 칸을 고르는데 화면 81%(682px)를 덮는 시트 + [적용하기]를 한 번 더 → AR-2
  - 헤더 [서비스 안내] — 자기 안내가 없는 화면(내가 쓴 글 · 설정 · 로그인 · 가입 · 없는 화면)에서 누르면 **목록으로 떠난다**(`RootLayout.tsx` `GuideButton`). 설정에는 이탈 확인이 없어(`useLeaveGuard`는 글 폼 · 댓글에만) 새 비밀번호를 치던 중이면 잃는다 → 질문 3
  - 휴대폰 쪽 넘김 — 같은 화면이지만 보던 카드를 통째로 갈아 끼운다 → AR-8
- **한 화면에 너무 몰린 곳** : 필터 시트(누를 것 16개) → AR-2 · 휴대폰 헤더(누를 것 4개가 4px 간격) → AR-6. 등록 폼 7칸이 한 화면인 것은 몰린 게 아니다(하지 말 것 1)
- **전환이 맞는 곳(유지)** : 목록 ↔ 상세(스크롤 · 포커스 복원), 등록 · 수정 성공 → 상세(기록 바꿈), 삭제 → 목록 · 보던 탭, 가입 → 자동 로그인 → 가려던 곳, 비밀번호 변경 → 로그인(백엔드가 모든 기기의 리프레시 토큰을 지운다), 댓글 수정 · 삭제와 사진 전부 삭제는 그 자리에서, 상세 · 등록에서 [서비스 안내]가 떠나지 않고 자기 안내를 연다

### 백엔드 필요 (프론트에서 만들지 않는다 — 보고만)

- **`PostListResponse`에 댓글 수** — 내가 쓴 글에서 어느 글에 답할 댓글이 있는지 카드에서 알게 된다(과업 ③의 입구). 지금은 글마다 열어 봐야 한다

- 새 댓글 알림은 2차 로드맵(알림)이라 범위 밖

## 2. 하지 말아야 할 것

1. **등록 폼을 여러 단계 화면으로 쪼개지 않는다.** 필수 6칸 + 사진이고, 한 화면 + 아래에 붙은 제출 줄이 가장 짧다. 단계마다 [다음] · 뒤로가기 · 이탈 확인이 늘고 "몇 칸 남았나"가 가려진다(힉스의 "작은 단계로 나누기"는 복잡한 작업에 쓰는 것)
2. **상세를 목록 위 모달 · 옆 패널로 띄우지 않는다.** 주소 공유 · 새 탭 열기 · 뒤로가기 · 스크롤 복원이 사용자가 아는 방식(제이콥)대로 동작하는 지금의 전체 화면이 맞다
3. **내가 쓴 글 카드에 상태 · 수정 · 삭제 버튼을 달지 않는다.** 카드 전체가 링크라 오터치가 생기고, 훑어보는 목록의 선택지가 카드마다 는다. 관리 동작은 상세 한 곳에 두고 대신 첫 화면으로 올린다(AR-4)
4. **떠 있는 버튼 · 붙은 줄을 더 늘리지 않는다.** 한 화면에 채운 강조는 하나다(폰 레스토프) — 목록 = 글쓰기 버튼, 상세 = 댓글 줄, 폼 = 제출 줄. 상세에 글쓰기 버튼을, 목록에 "맨 위로" 버튼을 더하지 않는다. 스크롤 방향에 따라 헤더 · 칩 줄을 숨겼다 보이는 것도 하지 않는다 — 누르려는 순간 움직인다(피츠)
5. **바로 반영을 글자 치는 칸까지 넓히지 않는다.** 장소를 한 글자 칠 때마다 목록이 다시 그려지면 무엇이 바뀌었는지 못 본다(기존 결정 유지). 바로 반영은 한 번 눌러 끝나는 카테고리 · 상태만(AR-2)

## 3. 다른 담당에게 묻고 싶은 것

1. **시각 담당** — AR-1 글쓰기 버튼(의도 전 잉크 / 뒤 개념 색)과 AR-3 댓글 줄이 첫 화면의 두 색 면 · 사진 위 배지와 강조를 다투지 않을 무게는? "그림자는 실제로 떠 있는 것에만" 규칙상 글쓰기 버튼은 그림자를 받는데, 어둡게 모드의 흰 채움 뒤집힘과 함께 어떤 모양이 AI 티 없이 읽히는가
2. **접근성 · 구현 담당** — AR-1 · 3 · 5를 다 하면 휴대폰 목록에 붙는 것이 헤더 57 + 칩 줄 ≈52 + 아래 버튼 ≈56px이 된다. 200% 확대 · 가로 휴대폰(높이 ≈375)에서 붙임을 끄는 높이 기준(제안은 30rem)이 맞는지, iOS 키보드가 AR-3의 아래 줄을 어떻게 다루는지(입력칸으로 데려간 뒤 줄이 키보드 위로 뜨지 않는지) 실제 기기 기준으로 봐 줄 수 있나
3. **온보딩 · 문구 담당** — 휴대폰 헤더의 [+]와 [?]를 둘 다 남길까? AR-1 뒤로 목록에서 [+]는 같은 일을 하는 둘째 입구가 되고, [?]는 상세 · 등록에서 화면 안의 (i)와 같은 것을 열며 그 밖의 화면에서는 목록으로 떠난다(설정에서 비밀번호를 치던 중이면 잃는다). 하나를 빼면 헤더 간격 문제가 AR-6 없이도 풀린다. 온보딩 1층 3단계의 대상을 휴대폰에서 AR-1 버튼으로 옮겨도 "개념 → 탐색 → 행동" 흐름이 유지되는가
