# 3차 반론 — 화면 구조 · 흐름 담당 (쟁점 ① ② ④만)

읽은 것 : `02_ui.md` · `02_review.md` · `02_api.md` · `02_security.md`. 리포는 고치지 않았다.

## 먼저 — 묻는 두 가지에 대한 답

**Q1. "숨기지 않는 떠 있는 버튼"이면 내 철회 근거가 풀리나?** — **푼다. 하지만 지금 나온 두 안은 둘 다 숨기는 버튼이다.**
- 사용자 담당 조건 : "의도 면 · 목록 끝 칸 · 빈 상태 버튼이 보이면 숨김(AR-1 그대로)"(`02_review` ②). 그때 입구는 "헤더 [+]뿐"이라고 직접 적었다. 결국 [주웠어요]를 누른 순간 쓸 수 있는 것은 오른쪽 위, 글자 없는 36px 선 버튼 하나다. 내가 AR-1을 철회한 이유가 그대로 남아 있다
- 데이터 담당 : 떠 있는 버튼에 더해 **그 화면의 헤더 [+]를 뺀다.** 이 경우 그 순간 화면에 보이는 입구는 **0개**다(목록 끝 칸은 ≈1,500px 아래). 지금보다 나빠진다
- 숨기는 조건을 "**의도를 고르기 전**에만 숨김"으로 고치면 풀린다. 고른 뒤에는 고른 면이 "선택된 상태"로 물러나고, 다음 동작은 "둘러보기 아니면 올리기"가 된다. 첫 화면에서 채운 강조끼리 다투는 문제도 고르기 전에만 생긴다

**Q2. 두 줄(하단 댓글 줄 · 칩 줄)과 떠 있는 버튼이 한 화면에 겹치면 총량 규칙에 맞나?** — **목록에서만 겹치고, 그때는 규칙 위반이다.**
- 상세 : 헤더 + 댓글 줄 = 2. 떠 있는 버튼은 목록 · 내가 쓴 글에만 있으므로 상세와는 겹치지 않는다 ✓
- 목록 : 헤더 + 칩 줄(④) + 떠 있는 버튼 = **3** ✗. 사용자 담당은 "버튼은 폭 일부라 예외"라고 했다. 하지만 이 규칙은 면적이 아니라 **개수**를 세는 규칙이다. 붙어 있거나 떠 있는 것은 하나마다 포커스 가림 · 짧은 알림 비킴 · `scroll-padding`을 따로 챙겨야 한다(`ui-ux-pro-max` Fixed Positioning "고정 요소를 겹겹이 쌓지 말 것", API2-3). 보안 담당도 "2개 이하 — 목록 = 글쓰기 **또는** 칩 줄"이라고 했다
- 둘 중 하나를 고른다면 **칩 줄**이다. 글쓰기는 헤더 [+](`?type` 실음)가 늘 있다. 반면 목록 중간에서 조건을 바꾸는 길은 칩 줄 말고는 없다. 대신할 길이 없는 쪽이 자리를 갖는다

## 쟁점별

| # | 상대 최강 근거(한 줄 인용) | 반박 / 인정 |
|---|---|---|
| ① | 시각 : "상세의 첫 화면은 '내 물건인가'를 판단하는 자리이고, 연락은 판단이 끝난 자리(본문 끝)에서 필요하다" | **반박.** 판단이 끝나는 곳은 본문 끝만이 아니라 댓글을 읽는 중간이기도 하다(45개 글은 입력칸까지 2,480px). 시각 담당 안의 "본문 바로 아래" 자리도 첫 화면 밖이다 — 사진 글은 y≈900, 긴 본문 글은 y≈1,277(`02_review` 실측). **사용자 담당 안은 인정하고 받는다** : 흐름 안 입구를 **배지 줄 오른쪽**(y≈210, 모든 폭에서 첫 화면 안)에 두고, 그 입구가 화면 위로 나간 뒤에만 하단 줄이 나타난다. 이러면 메타 줄 아래 자리를 고른 내 2차 안보다 낫다. 데이터 담당의 게이트 30rem은 40rem으로 맞춘다(568에서 22.2%) |
| ② | 데이터 : "⑥으로 목록이 길어지면 목록 끝 입구와 RV-2의 위쪽 링크는 둘 다 멀어진다" | **인정.** 96장을 내리는 동안은 엄지 쪽 입구가 필요하다. 다만 Q2 때문에 ④와 함께 정해야 한다. 헤더 [+]를 빼는 안에는 **반대**한다 — 사용자 담당 ⓐ(키보드 · 스크린리더 사용자는 문서 끝 버튼에 카드 24장 뒤에야 닿는다), ⓑ(화면마다 헤더 버튼 자리가 44px씩 바뀐다, WCAG 3.2.3), RV2-10(온보딩 3단계 대상) |
| ④ | 데이터 : "칩 줄이 필요한지는 목록 길이에 달렸다. 24건(4,139px)과 96건은 다른 문제다" | **인정.** 내 2차 AR2-4(④와 ⑥은 한 묶음)와 같은 말이다. "⑥을 먼저 만들고 다시 잰다"를 받는다. 사용자 담당의 폭 조건(22.5rem 미만은 줄바꿈한 두 줄을 붙이면 568의 27%)을 더한다 |

## 최종 표

| # | 채택안 | 조건 |
|---|---|---|
| ① | **흐름 안 입구(배지 줄 오른쪽, 모든 폭) + 휴대폰 하단 댓글 줄** — 둘이 동시에 보이지 않는다 | 줄은 폭 48rem 미만 · 높이 40rem 이상에서만 · 흐름 입구가 화면 위로 나간 뒤 나타나고 입력칸 · 로그인 권유 칸 · 복구 중 자리가 들어오면 숨는다(`IntersectionObserver`, 스크롤 방향 아님) · 입력칸은 붙이지 않는다 · `focus()`는 누름 처리 안에서 바로 · 로그인 복귀는 `#comment` → 댓글 제목에 포커스 · 짧은 알림은 `--bottom-inset` 위로(API2-3) |
| ② | **헤더 [+] 유지(`?type` · 이름 실음) + 목록 끝 칸.** 엄지 쪽 입구는 목록에 붙는 둘째 자리가 비어 있을 때만 | ④가 채택되면(칩 줄이 그 자리) : 떠 있는 버튼 없음 · RV-2 링크로 고른 순간을 맡는다 / ④가 보류 · 기각되면 : 떠 있는 버튼(폭 48rem 미만 · 높이 40rem 이상), **의도를 고르기 전에만 숨김**, 목록 끝 칸 · 빈 상태 버튼이 보이면 숨김. 이 경우 RV-2는 게이트가 꺼진 화면에서만 쓰는 대체 수단. 어느 쪽이든 헤더 [+]는 빼지 않고 온보딩 3단계 대상도 헤더 [+] |
| ④ | **⑥ [더 보기]를 먼저 내고, 그동안 목록에 붙는 것은 헤더만.** 96장 기준 "목록 중간 → 조건 바꾸기" 거리를 같은 도구로 잰 뒤 PM이 정한다 | 붙인다면 칩 줄만(검색칸 한 벌) · 높이 40rem 이상 · 폭 22.5rem 이상 · `scroll-padding-top` · 결과 제목 `scroll-margin-top` · 온보딩 `reveal()`에 칩 줄 높이를 더한다. **붙이면 ②의 떠 있는 버튼은 들이지 않는다**(목록 = 헤더 + 하나) |

총량 규칙(세 쟁점 공통) : 한 화면에 붙는 것 · 떠 있는 것은 **헤더 + 하나**. 둘째는 높이 40rem 이상에서만. 면적이 아니라 개수로 센다.
