# 03_api — 3차 반론 (데이터 · API 담당, 쟁점 ① ② ④ ⑧만)

읽은 것 : `02_ui.md` · `02_architect.md` · `02_review.md` · `02_security.md`. 리포는 고치지 않았다.

## ① 상세 연락 입구
- **상대의 가장 강한 근거(사용자 담당)** : "스크립트로 입력칸에 포커스하면 일부 휴대폰에서 누르지도 않았는데 키보드가 올라와 화면 절반을 덮는다. 로그인 뒤 복귀 포커스는 **댓글 제목**으로." 흐름 담당 실측도 받는다 — "RV-1 자리(메타 줄 아래)는 휴대폰 첫 화면 밖, y≈880~920".
- **인정** : 내 2차안은 "iOS는 동작 없이 키보드를 안 연다"만 봤다. 다른 휴대폰은 연다. 로그인 뒤 복귀는 **댓글 영역(제목)** 으로 고친다. 사용자가 직접 누른 입구에서는 입력칸 포커스를 그대로 둔다(동작 안이라 키보드가 뜨는 것이 맞다). 줄을 켜는 높이 기준도 30rem → **40rem**으로 양보한다(흐름 · 사용자 담당 공통 수치, 126/640 ≈ 20%).
- **반박(시각 담당)** : "연락은 본문 끝에서 필요하다"는 45개 댓글 글에서 입력칸까지 2,480px가 남는 문제를 풀지 못한다. 흐름 입구를 첫 화면(배지 줄)에 두면 시각 담당의 "가림 0"도 지켜진다.

## ② 휴대폰 글쓰기 입구 — 내 안을 거둔다
- **상대의 가장 강한 근거** :
  - 사용자 담당 : "목록에서만 헤더 [+]를 빼면 화면마다 헤더 자리가 44px씩 바뀐다(WCAG 3.2.3). 떠 있는 버튼은 문서 끝이라 키보드 사용자는 카드 24장 뒤에 닿는다. 온보딩 3단계 대상이 숨는다."
  - 흐름 담당 : "의도 면이 보이는 동안 숨기면 [주웠어요]를 누른 바로 그 순간 버튼이 없다."
- **인정** : 두 근거 모두 맞다. 헤더 [+] 제거는 철회한다. 그러면 남는 질문은 "헤더 [+](늘 붙어 있음 · `?type` 실음)에 떠 있는 버튼을 셋째 입구로 더할 것인가"다. 2차에서 내가 댄 근거("⑥으로 목록이 길어져 끝 입구가 멀어진다")는 **헤더가 붙어 있어** 헤더 [+]가 이미 어디서나 닿는다는 점을 빠뜨렸다. 데이터 비용은 양쪽 다 0이니, 붙는 것을 늘리지 않는 쪽(4명 중 3명)을 따른다. 떠 있는 버튼도 철회한다.

## ④ 스크롤 시 검색 · 필터 — 보류를 풀고 붙인다
- **상대의 가장 강한 근거(흐름 담당 AR2-4)** : "[더 보기]는 위로 데려가지 않는다. 96장(약 16,500px)을 내린 뒤 조건을 바꾸려면 그만큼 되돌아가야 한다. [더 보기]만 들이고 칩 줄을 안 붙이면 피츠가 지금보다 나빠진다."
- **인정** : 내가 설계한 [더 보기](B-3, "결과 제목으로 올리지 않는다")가 바로 그 원인이다. ②에서 떠 있는 버튼이 빠지면, 목록에 붙는 것은 헤더 + 칩 줄 = 2개다. 보안 담당의 "총량 2개 이하"를 넘지 않는다.
- **조건** :
  - 칩 줄만 붙이고 검색칸은 한 벌로 둔다.
  - 높이 40rem 이상 · 폭 22.5rem 이상에서만 붙인다(사용자 담당).
  - `--sticky-top` 하나로 스크롤 여백 4곳을 고친다(API2-4). 온보딩 `reveal()`도 칩 줄까지 잰다.
  - ⑥과 같은 묶음(묶음 2)에서 한다.
- **반박(시각 담당 "휴대폰은 붙이지 않음")** : 24건 쪽 넘김이었다면 맞다. 하지만 ⑥을 모든 폭 [더 보기]로 합의한 뒤에는 근거가 사라진다.

## ⑧ 완료 글 기본 제외 — 백엔드 형태 하나로
- **상대의 가장 강한 근거(사용자 담당)** : "UI가 필요로 하는 것은 '완료 아닌 것' 한 값뿐이다. 상태 묶음을 여러 개 고르기로 만들면 '누르면 반영 · 닫기'(③)와 맞지 않는다." 시각 담당 UI2-6도 같은 충돌을 짚었다.
- **인정** : 필터는 **하나만 고르기**로 유지한다. 2차에서 낸 "체크 여러 개"는 거둔다. 선택지는 흐름 담당 안대로 넷이다. `[진행 중](기본)` `[게시중]` `[연락중]` `[완료]`. 끝난 글을 섞어 보는 과업이 없어 `전체`는 뺀다.
- **반박 · 결정** : 화면이 "한 값"을 고르는 것과, 그 값을 API가 어떻게 받는지는 다른 문제다. 그 "한 값"을 받을 수 있는 백엔드 형태는 셋이다.
  - ⓐ `status` 반복 값 — 칸 타입을 `PostStatus` → `List<PostStatus>`로, `eq` → `in`으로 바꾼다. **필드가 늘지 않고**, 기존 단일 값 요청이 그대로 동작하며, 모순 조합이 없다.
  - ⓑ `excludeDone` — 필드를 하나 더하고, `status=DONE&excludeDone=true`의 규칙을 따로 정해야 한다.
  - ⓒ `ACTIVE` 같은 새 값 — 엔티티 Enum을 화면 사정으로 더럽힌다.
  - 백엔드를 직접 짜는 본인에게 가장 적게 바뀌는 쪽은 **ⓐ**다. 화면의 `[진행 중]`은 주소에 아무것도 쓰지 않는다(기본값). 요청할 때만 `status=OPEN&status=IN_PROGRESS`로 보내고, 나머지 셋은 지금처럼 한 값이다. 프론트 비용은 `QueryValue` 배열 지원(S) 하나다.

## 최종 표

| # | 최종 입장 | 바뀐 점 |
|---|---|---|
| ① | 흐름 입구는 **배지 줄 바로 아래**(모든 폭 · 첫 화면). 하단 줄은 **폭 48rem 미만 + 높이 40rem 이상**에서 흐름 입구가 화면 위로 나간 뒤에만 보이고, 입력칸이 보이면 숨는다. 직접 누르면 입력칸에 포커스, 로그인 뒤 복귀(`#comments`)는 **댓글 제목**에 포커스 | 높이 30 → 40rem, 복귀 포커스를 제목으로(양보) |
| ② | **떠 있는 버튼 없음.** 헤더 [+]는 모든 화면 같은 자리에 두고 `?type`을 싣는다. 의도를 고른 순간에는 RV-2 링크, 목록 끝 칸은 그대로. 온보딩 3단계 대상은 헤더 [+] | 내 안 둘 다 철회(헤더 [+] 제거 · 떠 있는 버튼) |
| ④ | **칩 줄만 붙인다**(높이 40rem · 폭 22.5rem 이상, 검색칸 한 벌, `--sticky-top`). 목록에 붙는 것은 헤더 + 칩 줄. ⑥과 같은 묶음 | 보류 → 채택(AR2-4 인정) |
| ⑧ | 필터는 **하나만 고르기** : `진행 중(기본)` · `게시중` · `연락중` · `완료`. 백엔드는 **`status` 반복 값**(`List<PostStatus>` + `in`, 서버 기본값은 그대로 모든 상태), 기본값은 주소에 안 쓴다. 의도 면 숫자도 같은 기준. 배포는 백엔드가 먼저, 머지 전에는 흉내 금지 | 여러 개 고르기 UI 철회 · `전체` 삭제 |
