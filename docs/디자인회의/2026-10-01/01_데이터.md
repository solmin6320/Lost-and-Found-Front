# 01_api — 데이터 · API 실현성 담당 1차 의견서

> 기준 : Front `main` `5e36160` · 백엔드 `c623a6a`(읽기만). 코드 · 리포 파일은 고치지 않았다.
>
> 한 줄 결론 : **화면 배치만 바꾸는 개선은 거의 전부 요청 0건이다.** 비싼 것은 "숫자"(건수)와 "쪽 이어 붙이기" 둘이다.
> 막히는 것은 거의 전부 백엔드의 세 가지에서 나온다. **`status` 가 값 하나뿐이고, 정렬이 고정돼 있고, 목록 응답에 없는 칸이 있다.**

|---|---|---|

### 1-B. 되지만 요청 수 · 캐시 비용이 커지는 것

| 개선안 | 지금 API로 가능? | 필요한 요청/캐시 변화 | 위험 | 비용 |
|---|---|---|---|---|
| 의도 칸 건수(지금 모습) | 예 | 첫 화면 3건 중 2건이다. 서버에서 건마다 글 SELECT(1건) + COUNT + **쓸데없는 썸네일 쿼리**가 돈다 | 건수와 결과 제목 옆 수를 받은 시각이 달라 잠깐 어긋날 수 있다. 지금은 검색어 · 필터가 걸리면 숫자를 빼서 피한다 | S(유지) |
| 의도 칸 건수를 "완료 빼고"로 | 부분 | 지금 API로는 유형마다 `전체 − 완료` 2건이 필요하다. 첫 화면이 **5건**이 된다 | 두 숫자를 서로 다른 시각에 받아 빼면 틀린 값이나 음수가 나올 수 있다 | M |
| 내가 쓴 글 탭 건수 3건(지금 모습) | 예 | 4건이다. 그런데 **지금 보고 있는 상태 탭의 건수는 본 목록의 `totalElements` 와 같다.** 1건은 중복이다(API-8) | 상태를 바꿀 때마다 4건을 다시 받는다 | S |
| 필터 [적용하기 · 12건] 미리 보기 | 예 | 고를 때마다 `size=1` 1건. 장소 글자는 300ms 멈춘 뒤에 보낸다. 같은 조건이면 캐시를 쓴다(키 정규화 `normalizePostListParams`) | 숫자가 늦게 따라와 버튼 글자가 흔들린다. 숫자 자리를 고정해야 한다. 서버에는 조작마다 COUNT가 돈다(D8) | M |
| 무한 스크롤(자동) + 뒤로가기 스크롤 복원 | 부분 | 조건마다 키 하나에 쪽 N개가 쌓인다. **무효화(글 올리기 · 상태 변경 · 닉네임 변경) 때 받아 둔 N쪽을 순서대로 N번 다시 받는다.** 뒤로가기는 5분(gcTime) 안이면 캐시로 바로 높이가 찬다. 5분이 지났거나 새로고침했으면 1쪽만 남아 위치를 찾지 못한다(`ScrollMemory.tsx:20` 은 1.2초 기다린 뒤 닿는 데까지만 간다) | D1 겹침 · 누락, 새로고침 뒤 위치 잃음. 목록 끝 "찾는 물건이 없나요?" 칸에 영영 닿지 못한다 | L |

| 방금 올린 글 바로 반영(지금 구조 그대로) | 부분 | 지금 흐름 : 등록 → `lists()` 무효화 → 상세로 이동(상세 1건). 목록으로 돌아오면 **옛 캐시를 먼저 그리고**, 새 글이 맨 위에 끼면서 카드가 한 칸씩 밀린다. 목록 캐시에 응답을 직접 끼워 넣기는 어렵다. 사진 주소가 없고(D5), 검색어가 본문까지 보는 조건을 앞에서 똑같이 흉내 내야 해 틀리기 쉽다 | 카드가 밀리고, 포스터가 사진으로 바뀌며 번쩍인다. 대안은 API-4 | M |

### 1-C. 백엔드가 있어야 되는 것(보고만 한다 · 개선 목록 번호 연결)

|---|---|---|---|---|
| 완료 글 기본 제외 | 백엔드 필요 | `status` 를 `List<PostStatus>` + `in` 으로 바꾼다(또는 `excludeDone=true`). 프론트는 `QueryValue` 가 배열을 싣지 못한다(`client.ts:118`). 같은 이름 반복을 지원하고, 주소 규칙과 기본값을 정한다 | 앞에서 걸러 내면 "25건"이라고 해 놓고 18장만 보인다(하지 말 것 3) | S / S |

## 3. 하지 말아야 할 것

1. **카드에 손가락이나 마우스만 올려도 상세를 미리 받기.** 상세 GET은 조회수를 올리는 쓰기다(D4). 열지도 않은 글의 조회수가 오르고, 요청마다 쓰기 트랜잭션과 1일짜리 키가 쌓인다. 빨리 보이게 하고 싶으면 목록 캐시로 머리부터 그린다(API-3).
2. **주소에 흔적 없이 쪽을 자동으로 이어 붙이는 무한 스크롤.** 새로고침 · 링크 공유 · 5분 뒤 뒤로가기가 모두 1쪽으로 돌아간다. offset(D1)이라 붙일 때마다 겹치거나 빠진다. 목록 끝 "찾는 물건이 없나요? [분실 글 올리기]" 칸에도 영영 닿지 못한다. [더 보기] + 주소로 한다(API-2).
3. **백엔드가 못 하는 일을 앞에서 흉내 내기.** 받은 24장에서 완료 빼기, 한 쪽 안에서만 인기순으로 다시 줄 세우기, 두 상태를 따로 받아 섞기, "5번째 실패 시각"으로 잠금 남은 시간 추정하기가 여기에 든다. 결과 수 · 순서 · 시간이 **사실과 달라지고**, "숫자까지 알린다"는 결과 고지 규칙이 깨진다.
4. **게시글 응답을 기기 저장소에 넣기**(최근 본 글 카드, 오프라인 목록 등). 보안명세서 3장이 금지한 항목이다. 공용 기기에 남고, 지워진 글 · 완료 글이 낡은 모습으로 보인다.

## 4. 다른 담당에게 묻고 싶은 것

1. **(목록 · 정보 구조 담당)** 완료를 기본에서 빼면 "주인에게 돌아간 사례"가 피드에서 사라진다. 신뢰 신호로 남길 입구가 필요한가? 상태 묶음의 [완료 포함] 하나면 충분한가, 아니면 목록 끝 "주인에게 돌아간 물건 N건" 한 줄이 필요한가? 정해 주면 백엔드에 `status` 다중 값과 `excludeDone` 중 어느 쪽을 요청할지 고르겠다.
2. **(모션 · 시각 담당)** [더 보기]를 "크기를 늘려 다시 받기"로 하면, 그사이 새 글이 올라왔을 때 누르는 순간 카드 전체가 한 칸 밀린다(드문 일이다). 이 밀림을 부드럽게 이어 주기만 할지, 아니면 새 글은 맨 위에 "새 글 1건 [보기]" 한 줄로 따로 알리고 목록은 고정할지? 후자는 응답의 첫 id 만 비교하면 돼서 요청이 늘지 않는다.
