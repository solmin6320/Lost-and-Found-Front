## B. 쟁점 ①~⑧ — 최종 입장

| # | 쟁점 | 최종 입장 | 근거(데이터 · 법칙) | 타협 · 조건 |
|---|---|---|---|---|
| ① | 상세 연락 입구 | **휴대폰은 하단 고정 줄**(UI-4 · AR-3). 화면 높이 30rem 미만이면 줄을 끄고 **배지 줄 아래 흐름 안 링크**(RV-1의 모양)로 바꾼다. 넓은 화면은 `댓글 N` 제목 옆 링크 | 요청 0. "내 물건이다"를 판단하는 순간 손은 사진 · 정보 근처(첫 화면 아래쪽)에 있다. 위쪽 링크는 이미 지나갔다(피츠). RV-1이 걱정한 가림은 확대 · 가로 화면에서 가장 크다. 그 경우만 끄면 남는 가림은 등록 폼 제출 줄과 같은 수준이다 | 한 화면에 입구는 하나만 보인다. 상세 설계는 B-1 |
| ② | 휴대폰 글쓰기 입구 | **AR-1 떠 있는 버튼**. 같은 화면에서는 헤더 [+]를 뺀다(UI 하지 말 것 1). 다른 화면의 헤더 [+]는 남긴다 | 요청 0. ⑥으로 목록이 길어지면 목록 끝 입구와 RV-2의 위쪽 링크는 둘 다 멀어진다. 숨김은 IntersectionObserver로만 판정한다(`total`로 하면 깜빡인다) | 버튼 자리 때문에 Flash를 올린다(API2-3). 온보딩 3단계의 대상도 같이 옮긴다 |

### B-1. ① 연락 입구 — 설계

1. **휴대폰(48rem 미만, 높이 30rem 이상)** : 아래에 붙는 줄 하나. 무엇을 보여 줄지는 보는 사람에 따라 다르다.
   - 방문자 · 로그인 : `[댓글 남기기 · 45]`
   - 비로그인 : `[로그인하고 댓글 남기기]`
   - 글쓴이 : `[댓글 5개 보기]` — 댓글 제목으로 데려간다
   - 완료 글 : 선 버튼
   - 줄 안에 입력칸은 넣지 않는다.
2. **숨김** : 입력칸 · 로그인 권유 칸 · 세션 복구 중 자리 칸 가운데 하나가 화면에 들어오면 줄을 숨긴다(IntersectionObserver). 숨겨진 동안 문서 아래 여백(`scroll-padding-bottom`)도 0으로 돌린다.
3. **누름**
   - 로그인 : 입력칸 `focus({ preventScroll: true })`를 **누름 처리 안에서 바로** 부르고, 이어서 `scrollIntoView({ block: 'center' })`(모션 줄이기면 즉시). 휴대폰 키보드는 이렇게 해야 열린다.
   - 비로그인 : 로그인 권유 칸의 링크로 포커스를 옮긴다.
4. **숫자** : 제목과 같은 `total`을 쓴다. `CommentSection`이 값을 올려 주거나, 공용 선택 함수를 하나 둔다.
5. **새 댓글 위치** : 입력칸 자리는 목록 끝 그대로다. 그래서 방금 남긴 댓글은 지금처럼 입력칸 바로 위의 `fresh` 목록에 붙는다. 서버 정렬(오래된 순 고정, `CommentService.java:58`)을 바꿀 필요가 없다. → 1차의 "입력칸 옆에 방금 남긴 댓글" 우려는 **철회**한다.
6. **로그인 뒤 입력칸으로 돌아오기**(RV-1 선택안) — 기존 규칙을 해치지 않고 된다.
   - 권유 칸의 로그인 링크를 `loginPath(\`${here}#comments\`)`로 만든다. `safeRedirectPath`는 해시를 살린다. 기존 테스트 `/posts/12#comments`가 이미 통과한다(`authRedirect.test.ts:14`). 열린 리다이렉트 검사는 손대지 않는다.
   - 돌아오면 `<Navigate replace>`로 경로가 바뀐다. ScrollMemory는 맨 위로, RouteFocus는 h1으로 보낸다(지금 규칙 그대로).
   - 상세는 해시가 `#comments`이면 **상세 · 댓글 다시 받기가 끝난 뒤**(최대 1.5초) 입력칸으로 데려가 포커스를 준다. 로그인은 `postKeys.all`을 무효화한다(API2-1).
   - 그다음 `navigate({ hash: '' }, { replace: true, state: location.state })`로 해시를 지운다. 새로고침 · 공유에서 또 끌려가지 않게 하려는 것이다. 경로가 같으니 ScrollMemory와 RouteFocus는 둘 다 건드리지 않는다. RouteFocus가 먼저 h1에 가 있었어도 `focusMovedElsewhere()`가 손을 뗀다.
   - 쓰던 댓글 보관(`CommentDraftOffer`)이 있으면 그쪽이 먼저다. 이미 그 자리로 데려온다.
   - 해시로 돌아오는 경우는 사용자 동작이 아니다. 그래서 iOS에서는 키보드가 열리지 않고 포커스만 간다. 오히려 낫다(키보드가 갑자기 화면을 덮지 않는다).
7. **함께 고칠 것** : API2-2(로그인을 거쳐 돌아온 상세의 [목록으로]가 보던 목록을 잃는다).

5법칙 점검
- 힉스 : 선택지 +0(줄은 동작 하나)
- 피츠 : 0 ~ 2,480px → 0, 엄지 자리, 높이 44 이상
- 제이콥 : 등록 폼 제출 줄과 같은 틀
- 근접성 : 넓은 화면은 제목 바로 옆
- 폰 레스토프 : 이 화면의 잉크 채움은 이 버튼 하나, 완료 글은 선 버튼

### B-2. ③ 필터 — 설계와 [초기화]의 뜻

| 칩 | 여는 것 | 반영 | 지우기 |
|---|---|---|---|
| 카테고리 | 그 묶음만(휴대폰은 작은 바텀 시트, 넓은 화면은 칩 바로 아래 펼침 — 새 부품 `PostFilterPopover`) | 칸을 누르면 **바로 반영하고 닫힌다.** 포커스는 값이 든 칩으로 돌아온다(지금 `refocus.chip` 그대로) | 첫 칸 `전체`가 지우기다 |

  - 바로 반영은 누를 때마다 1건이다. 카테고리 + 상태를 걸면 1건 → 2건(서버 COUNT 1회 더). 받아들일 만하다.
  - 조건마다 기록이 쌓인다(`usePostListSearch`는 push). 그래서 뒤로가기 한 번이 "방금 고른 것 되돌리기"가 된다. 덤으로 생기는 이점이다.

- **API-5(적용하기 · 12건 미리 보기)** 는 장소 · 기간 시트에만 남는다. 범위가 줄어 P2 그대로다.
- **API-7(검색어 → 카테고리 제안)** 은 누르면 바로 반영되는 쪽과 뜻이 맞는다. 제안 한 번이 칩 한 번과 같다.

5법칙 점검
- 힉스 : 한 번에 보이는 선택지 16 → 6(카테고리) · 4(상태) · 장소 · 기간 시트는 그대로
- 피츠 : 넓은 화면은 누른 칩 바로 아래, 휴대폰은 작은 시트
- 제이콥 : 칩 = 그 조건, 뒤로가기 = 되돌리기
- 근접성 : 열린 판이 그 칩에 붙는다

### B-3. ⑥ [더 보기] — 스크롤 복원과 함께 구체 설계

**주소와 요청**
- `?page=n` = **"24건 묶음을 n개까지 펼쳤다"**(1부터). 폭과 상관없이 뜻이 하나다. 목록의 `Pagination`은 뺀다. 내가 쓴 글(SCR-07)은 탭 · 쪽 번호 그대로 둔다(글 수가 적다).
- n ≤ 4 : `page=0&size=24n` **한 번**에 받는다(최대 96, 서버 상한 100 — `application.yml:28`). 쿼리 키도 하나다.
- n > 4 : 앞 96건 쿼리 + 뒤 `page=k, size=24`(k = 4…n−1)를 `useQueries`로 받아 이어 붙인다. id로 겹침을 거른다. offset이 겹치거나 빠질 위험(D1)은 **이 구간에만** 남는다. 드문 경로다.

**누를 때**
1. 새 함수 `expand()`(`usePostListSearch`)로 `setSearchParams(next, { replace: true })` 한다. 기록을 쌓지 않아서 뒤로가기가 "덜 펼친 목록"이 아니라 이전 화면으로 간다.
   - ScrollMemory : 경로가 같아 위치를 건드리지 않는다. 새 `location.key`에 이어서 적는다.
   - RouteFocus : 경로가 같아 아무것도 하지 않는다.
2. 지금의 `handlePageNavigate`(결과 제목으로 올리기)는 **부르지 않는다.**
3. **격자를 흐리게 하지 않는다.** 지금은 키가 바뀌면 격자 전체에 `data-stale`이 붙는다(`PostListPage.tsx:363`). 이미 본 24장이 통째로 흐려졌다 돌아오면 깜빡임이 된다. "쪽 수만 늘어난 변화"일 때는 버튼만 `불러오는 중…`(`aria-disabled`)으로 바꾼다.
4. 응답이 오면
   - **화면 고정** : 누르기 전 마지막 카드(id)의 화면 위치를 `useLayoutEffect`에서 재어 그대로 둔다(`scrollBy(차이)`). 그사이 새 글이 맨 위에 끼어 카드가 한 칸씩 밀려도 보던 자리가 움직이지 않는다. CSS 스크롤 고정(`overflow-anchor`)을 지원하지 않는 브라우저도 있어 직접 한다. 요청은 0이다.
   - **포커스** : 그 마지막 카드의 **다음 카드**로 옮긴다(`focus({ preventScroll: true })`). 자리 순서가 아니라 id 기준이다. 밀림이 있어도 "본 것 바로 다음"에서 이어 읽는다.
   - 알림 영역 : `24건을 더 불러왔어요. 48 / 57`
5. **실패** : 받아 둔 카드는 그대로 두고, 버튼 아래에 서버 문장 + [다시 시도]를 띄운다.
6. **끝** : 보인 수가 전체 수 이상이면 버튼을 빼고, 바로 아래 "찾는 물건이 없나요?"(`PostIntentNext`)에 닿는다. 자동 무한 스크롤에서 막히던 그 칸이다.

**돌아올 때 · 새로고침**
- 5분 안에 뒤로가기 : 캐시(`size=24n`)에서 바로 그려져 높이가 같다. ScrollMemory가 그대로 맞춘다.
- 새로고침 · 5분 뒤 · 새 탭 : 요청 1건이다. 이때 **스켈레톤 수를 `min(24n, 96)`으로 늘린다**(지금은 12 고정 — `SKELETON_COUNT`). 카드 사진은 `aspect-ratio: 1`이고 제목은 2줄까지라, 높이가 응답 전에 거의 맞게 잡힌다. 그러면 ScrollMemory의 1.2초 기다림(`RESTORE_WAIT_MS`) 안에 목적지에 닿고, 스켈레톤이 같은 자리에서 카드로 바뀐다(CLS 0). ScrollMemory 코드는 고치지 않는다.
- 남는 한계 : RouteFocus는 누른 카드를 600ms까지 기다린다. 응답이 그보다 늦으면 h1로 간다(`preventScroll`이라 스크롤은 맞다). 지금 쪽 번호에서도 똑같은 한계다.

**캐시 · 무효화**
- 글을 올리거나, 상태를 바꾸거나, 지우면 지금 보는 목록 **1건**만 다시 받는다(`size=24n`).
- 조건을 바꾸면 `page`는 1로 돌아가고 기록에 쌓인다(지금 `update` 그대로).
- 빈 상태 `past-end`는 n > 4 구간에서만 생길 수 있다.

**선택(P2)** : [더 보기]가 화면에 들어오면 다음 묶음을 미리 받는다. 목록 GET은 조회수를 쓰지 않아 상세와 달리 허용된다. 다만 누르지 않으면 1건이 헛돈다(D8). 인덱스가 생긴 뒤에 본다.

5법칙 점검
- 힉스 : 이전 · 번호 · 다음 → 버튼 하나
- 피츠 : 마지막 카드 줄 바로 아래 · 폭 전체 · 44px 이상
- 제이콥 : 사진 피드는 아래로 이어진다 + 뒤로가기 · 새로고침이 보존된다
- 근접성 : 버튼은 카드 줄에 붙고, "찾는 물건이 없나요?"와는 24px 넘게 떨어진다
- 폰 레스토프 : 선 버튼. 이 구역의 채움은 의도 색 버튼 하나

### B-4. ⑧ 완료 글 기본 제외 — 백엔드 요청 형태와 근거

**고른 것 : `status` 반복 값.** 백엔드에 보고만 한다. 수정 · 커밋은 본인이 한다.

- `PostSearchCondition.status` : `PostStatus` → `List<PostStatus>`(이름은 `status` 그대로)
- `statusEq` → `statusIn` : 비었거나 `null`이면 조건 없음, `null` 원소는 버리고 `post.status.in(list)`
- 서버 기본값은 **지금처럼 모든 상태**. 지금의 단일 값 요청(`?status=OPEN`)은 원소 하나짜리 목록으로 그대로 묶인다. 다른 호출자와 기존 테스트가 깨지지 않는다.
- 백엔드 테스트 제안 : `?status=OPEN` · `?status=OPEN&status=IN_PROGRESS` · `?status=OPEN,IN_PROGRESS`(쉼표도 묶이는지 확인해 문서에 적는다) · `?status=WRONG` → 400 · `?status=` → 조건 없음(빈 값이 `null` 원소가 되어 `in (null)` → 0건이 되지 않는지)
- 내 글(`/api/members/me/posts`)은 그대로 둔다. 탭이 상태 하나씩이다.

**`excludeDone`을 고르지 않은 이유**
1. `status=DONE&excludeDone=true` 같은 **모순 조합**이 생긴다. 400으로 할지 빈 결과로 할지 규칙을 하나 더 정해야 한다. 반복 값에는 모순이 없다.
2. 화면 정책("기본은 뺀다")이 API 이름에 박힌다. 기본값을 바꾸려면 API를 바꿔야 한다. 반복 값이면 정책은 화면에, API는 "고른 상태들"만 안다.
3. 여러 상태 필터가 나중에 다시 필요할 때(예 : 내 글 "진행 중" 묶음) 또 손대지 않아도 된다.
4. 백엔드 학습 관점에서도 "목록 바인딩 + `in`"은 다른 필터에 다시 쓰는 일반 기술이다.
- `excludeDone`의 장점도 인정한다. 프론트 `client.ts`를 고치지 않아도 되고, 잘못 배포하면 완료 글이 보여 눈에 띈다. 하지만 배열 지원은 S이고, 배포 순서는 규칙으로 막는다(API2-8).

**프론트(머지 · 배포 뒤 — 그 전에는 지금 모습 그대로)**
- `QueryValue`에 `readonly string[]`을 더한다. `buildUrl`은 같은 이름으로 `append`하고 빈 원소는 건너뛴다.
- `normalizePostListParams` : 상태 배열을 Enum 순서로 정렬하고 중복을 없앤다. **셋 다 고르면 뺀다.** 같은 결과가 같은 캐시 키 하나를 쓰게 하려는 것이다.
- 주소 어휘
  - `status` 없음 = 찾는 중(기본, `OPEN` + `IN_PROGRESS`)
  - `status=DONE`
  - `status=ALL`
  - 옛 링크 `status=OPEN` · `IN_PROGRESS`도 읽는다
- 필터 상태 묶음 : `찾는 중(기본) · 완료 · 전체` 셋을 권한다. 게시중 · 연락중을 하나씩 거르는 칸을 남길지는 PM이 판단한다. 내가 쓴 글 탭에는 그대로 있다.
- 의도 칸 건수 : `{ type, status: [OPEN, IN_PROGRESS], size: 1 }`. 요청 수는 2건 그대로다. 결과 제목의 수와 같은 기준이라 숫자가 서로 맞는다.
- "완료 포함" 입구
  - 상태 묶음의 `완료` · `전체`
  - 목록 끝 한 줄 `완료된 글은 빼고 보여 줘요 · [완료 글도 보기]` — 요청 0. 숫자는 넣지 않는다. 넣으면 조건마다 +1건이고, 인덱스(D8) 뒤에 다시 본다
  - 빈 상태와 검색 0건에도 같은 링크를 둔다
  - 기본값일 때 상태 칩에는 값을 적지 않는다. 숨은 조건이 되지 않게 하는 일은 끝 줄이 맡는다
- 금지(머지 전후 모두) : 받은 24장에서 앞에서 걸러 내기, 두 상태를 따로 받아 섞기(하지 말 것 8).

5법칙 점검
