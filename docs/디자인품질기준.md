# 디자인 · UI/UX 품질 기준

이 프로젝트에서 **가장 우선하는 가치**다. 기능이 동작하는 것은 최소 조건이고, 여기 적힌 것을 만족해야 "끝났다"고 말한다.

`front-design-rules` 스킬이 **이 서비스의 구체적 규칙**(배지 체계, 결과 고지 문구 등)을 담는다면, 이 문서는 **모든 화면에 적용되는 품질 기준**이다. 아래 "기준 스킬 7개 + UX 5법칙"과 함께 읽는다.

---

## 최우선 원칙 — 언제나 사용자 먼저 (본인, 2026-09-26)

> "언제나 사용자를 먼저 생각. UI·UX, 디자인, 편안함, 피로감을 덜고, 가독성을 올리고, 기능이 잘 보이게."

이 문서의 모든 규칙과 스킬 규칙보다 **먼저** 적용한다. 규칙끼리 부딪히면 이 기준으로 가른다.

| | 이 프로젝트에서 뜻하는 것 |
|---|---|
| 피로감을 던다 | 큰 면에 채도 최대치 색을 오래 보게 하지 않는다(마리골드 넓은 면을 한 단계 낮춘 이유). 어둡게 모드. 움직임은 누른 것에만 |
| 가독성 | 본문 16px 하한 · 행간 1.7 · `keep-all` · 대비 AA 이상(계산) · 위계는 크기보다 굵기와 색 |
| 기능이 잘 보이게 | 주요 동작은 찾지 않아도 보이는 곳에. 아이콘만 있는 버튼엔 이름(`aria-label`)과 이름표(툴팁). 숨은 제스처 금지 |
| 편안함 | 누르는 면적 44px · 되돌릴 수 있게 · 결과는 누르기 전에 · 막다른 길 없음 |

## AI 티를 아예 뺀다 (본인, 2026-09-26)

`design-taste-frontend`의 9장(AI Tells) · 14장(Pre-Flight)을 체크리스트로 끝까지 돌린다. `ui-ux-pro-max`는 **UX 규칙 · 점검표만** 쓴다 —
`--design-system`이 주는 색(Tailwind 파랑 + 주황)과 폰트(한글 없는 Outfit)는 그 자체가 AI 기본값이라 쓰지 않는다.
프로젝트 결정(Pretendard, CSS Modules, 분실 · 습득 두 개념 색, 사진 위 유형 배지, 칠한 포스터 그림)이 스킬 기본값보다 우선한다.

| AI 티 | 바꾼 것 |
|---|---|

| 전부 크게 둥근 반경(14~22px 일곱 단계) | 네 단계, 가장 큰 면도 12px(아래 1장) |
| Tailwind 파랑과 같은 코발트(`#2F5CE0` ≈ `#2563EB`, ΔE00 2.8) | `#2F5FB1`(Tailwind blue-600과 ΔE00 7.2) — 보관소 · 안내 창구의 차분한 파랑. ~~ΔE 3.6 → 31.8~~은 척도를 적지 않은 CIE76(Lab 직선 거리) 값이었다(2026-10-12 정정). **다만 Material blue 800 `#1565C0`과는 ΔE00 3.4** — 아래 "색 거리" 기준에 못 미친다 |

**남겨 둔 예외** — 본인이 좋다고 한 요소다. 바꿀 때는 대안을 만들어 **나란히 비교**해 보여 주고 본인이 고른다.

- 칠한 카테고리 포스터 그림(직접 그린 SVG) — 대안(Phosphor 큰 글리프)을 만들어 비교 스크린샷을 남겼다
- 사진 위 유형 배지 — "이미지 위 알약 금지"에 걸리지만 "내 물건인가"를 1초 안에 가르는 핵심 정보다
- 설정 화면의 화면 모드 미리보기(div 도식) — "가짜 스크린샷 금지"에 걸리지만 본인 목업이고, 실제 토큰으로 그리는 진짜 컴포넌트 미리보기다
- 상세 사진 오른쪽 아래 `크게 보기` 표시(작은 어두운 원) — "사진 위 겹침 금지"에 걸리지만 장식이 아니라 누르면 커진다는 조작 표시다. 글자 없이 아이콘 하나, 누르는 면은 사진 전체
- 등록 · 수정의 사진 칸 위 `×` · `‹` `›`(28px 원, 누르는 면 44px)와 첫 장의 `대표` 이름표(2026-09-27) — 같은 이유로 장식이 아니라 조작 · 상태다. 버튼을 사진 밖 줄로 빼면 375 폭 3열에서 칸이 버튼 셋을 담지 못한다
- 등록 · 수정의 "목록에서 이렇게 보여요" 미리보기(2026-09-27) — 가짜 화면이 아니라 목록과 같은 카드 컴포넌트를 입력값으로 그린 것이다

### 색 거리 — 강조색만, 기본 · 금지 팔레트와 ΔE00 5 이상 (본인 결정 2026-10-12)

- **척도는 CIEDE2000(ΔE00)** 하나다. 숫자에는 늘 척도 이름을 붙인다. 예전 문서의 `ΔE 3.6 · 31.8 · 105`는 CIE76(Lab 직선 거리)이라 같은 두 색도 훨씬 멀어 보였다(→ ΔE00 2.8 · 7.2 · 57 이상)
- **강조색에만 잰다** — 분실 · 습득 면, 배지, 버튼(채움 · hover). 기본 팔레트 **Tailwind v3 · Bootstrap 5(단계 100~900) · Material(2014 팔레트)** 와 **금지 팔레트**(`design-taste-frontend` 4.2 크림 · 놋쇠 · 에스프레소 16색)에서 가장 가까운 색까지 **ΔE00 5 이상**. 5 미만이면 "같은 색"으로 본다(예전 "ΔE 10 미만이면 같은 색"은 척도도 범위도 없어 폐기)
- **중성색(회색 · 검정 · 종이)은 ΔE로 보지 않는다** — 기본 팔레트의 회색 다섯 벌(slate · gray · zinc · neutral · stone)이 회색 공간을 촘촘히 덮어, ΔE로 빼려 하면 회색이 엉뚱한 색을 띤다. 대신 **색 온도 일관성**(종이 · 잉크 · 선이 같은 온도 — 따뜻한 회색과 찬 회색을 섞지 않는다, `design-taste-frontend` 4.2 "One palette per project")과 **쓰임**(글자 대비 · 위계 · 어둡게의 눈부심)으로 본다
- 지금 값(2026-10-12 실측) — **강조색 아홉 모두 기준에 못 미친다.** 색 조합은 비교 캡처를 본 뒤 본인이 고른다(회의결과 7-2), 고르기 전에는 `tokens.css`를 바꾸지 않는다

| 강조색 | 값 | 가장 가까운 기본 팔레트(ΔE00) |
|---|---|---|
| 마리골드 배지 · 버튼 | 밝게 `#FFBF2E` · 어둡게 `#EBB33F` | Material yellow 700 `#FBC02D` **1.3** · Tailwind amber-400 `#FBBF24` **1.4** / 어둡게 Tailwind yellow-500 3.8 |

| 마리골드 hover | `#F5A900` | Material amber A700 2.0 |
| 코발트 면 · 배지 · 버튼 | `#2F5FB1` · `#3765B8` | Material blue 800 `#1565C0` **3.4** · Bootstrap blue-600 3.7 · Tailwind blue-600 7.2 / 어둡게 Material blue 800 2.7 |
| 코발트 hover | `#264F97` · `#3C69BB` | Material blue 900 3.1 / 어둡게 Material blue 800 3.2 |

## 기준 스킬 7개 + UX 5법칙 — 매번 본다 (본인, 2026-10-02)

> "이 기준 스킬들과 효과, 법칙들은 에이전트들이 디자인, UI/UX, 구조, 위치 + 크기, 색깔, 글꼴 등등 모든 구조를 수정 및 개선 및 추가할 때마다 기준점으로 봐야 해(매번 보란 소리)"

### UX 5법칙

조사 근거는 아래 "출처", 우리 화면 적용 사례는 `docs/디자인회의/2026-10-01/`(`00_안건.md` · `04_회의결과.md`).

| 법칙 | 뜻 | 우리 화면에서 | 잘못 쓰면(하지 않는다) |
|---|---|---|---|
| **힉스의 법칙** (Hick–Hyman) | 선택지의 수 · 복잡도가 늘수록 결정이 느려진다 | 한 순간에 보이는 선택지를 줄인다(칩 하나 = 묶음 하나) · 기본값 · 추천을 드러낸다 · 기능은 점진적으로 | 단순 결정에만 맞는다 — 사진 피드를 고르는 일은 대상이 아니다. 줄이다 뜻이 흐려지면 역효과. 결과 고지 · 개인정보 줄은 안전이라 줄이지 않는다. 등록 폼을 여러 화면으로 쪼개지 않는다 |
| **피츠의 법칙** (Fitts) | 누르는 시간은 거리와 크기의 함수 — 크고 가까울수록 빠르고 정확하다 | 누르는 면 44px · 사이 8px 이상 · 아이콘 + 글자 · 자주 쓰는 동작은 손 · 시선 가까이 · **위험 동작은 16px + 모양 차이로 떼고**, 확인 버튼은 열린 뒤 0.5초 누름 무시 | "전부 크게"가 아니다(44px는 누르는 면의 하한). 화면 가장자리 이점은 마우스만. 떠 있는 버튼 · 붙는 막대를 늘려 콘텐츠를 가리지 않는다(8장 "붙는 것 총량 규칙") |
| **제이콥의 법칙** (Jakob Nielsen) | 사람은 대부분의 시간을 다른 서비스에서 보낸다 → 아는 방식대로 동작하길 기대한다 | **동작과 자리**는 관례대로(뒤로가기 · 주소 공유 · 오류는 칸 아래 · 제출 줄 · 링크 모양) | **생김새는 따라 하지 않는다**(관례의 겉모습을 들이면 템플릿이 된다 — AI 티 배제). 리포 문서에 외부 서비스 이름을 쓰지 않는다("국내 앱 공통 관례") |
| **근접성의 법칙** (게슈탈트) | 가까이 있는 것은 한 묶음으로 보인다 | **묶음 안 간격 < 묶음 사이 간격**(라벨–칸 4~8px, 묶음 사이 24px 이상) · 관련 동작은 대상 바로 옆(안내는 설명 대상 바로 뒤, 남은 칸 수는 제출 버튼 바로 위) | 근접성은 색 · 모양보다 세다 — 묶음이 실제 관계와 맞아야 한다. 관련 버튼을 무관한 버튼 사이에 묻지 않는다. 구분선 대신 간격으로 가른다 |
| **폰 레스토프 효과** (격리 효과) | 비슷한 것들 사이에서 다른 하나가 가장 잘 기억된다 | 한 화면 · 한 구역의 주 동작 하나만 튀게(색 면 한 묶음 + 잉크 채움 하나) · 필요한 곳에 강조(연락 입구 · 완료 글 · 방금 틀린 칸 · 개인정보 · 안전 경고 — 빨간 글자 + 세모) | **강조를 아낀다.** 색만으로 구분하지 않는다(글자 · 아이콘 · 모양 함께). 움직임 · 깜빡임으로 강조하지 않는다. 광고처럼 보이지 않게. 사용자가 칠 수 있는 모양(`!` · `[공지]` · 글자 기호)을 시스템 표시로 쓰지 않는다 |

**매번 점검표** — 바꾸는 것마다 결과 보고에 한 줄씩
1. 힉스 : 이 순간 보이는 선택지가 늘었나 줄었나, 기본값 · 추천이 보이나
2. 피츠 : 누를 곳의 크기 · 사이 간격 · 손에서의 거리, 위험 동작과의 거리
3. 제이콥 : 사용자가 기대하는 자리 · 동작인가(생김새는 우리 것인가)
4. 근접성 : 묶음 안 < 묶음 사이 간격, 관련 요소가 붙어 있나
5. 폰 레스토프 : 이 구역에서 튀는 것이 하나뿐인가, 색 말고 모양으로도 구분되나

법칙끼리, 또는 법칙과 위 원칙(사용자 먼저 · AI 티 배제 · 부드럽게 잇는 모션)이 부딪히면 **사용자 먼저**가 이긴다.

## 1. 첫인상 — 템플릿처럼 보이지 않는다

AI가 만든 화면에는 반복되는 기본값이 있다. 그게 보이면 "대충 만들었구나"로 읽힌다.

| 피할 것 | 대신 |
|---|---|
| 모든 모서리를 같은 반경으로 · 전부 크게 둥글게 | **물성으로 고르는 네 단계**(아래 표). 가장 큰 면도 12px |
| 카드마다 그림자 | 목록 카드는 그림자 없이 **잉크 윤곽 3px 한 줄**이 카드 한 장(사진 + 글 칸)을 두른다(본인 피드백 2026-10-08로 덮어씀 — 예전은 "테두리 없이 사진의 사각형이 카드"). 그림자는 **실제로 떠 있는 것**(모달·시트)에만 |
| 보라 그라데이션, 크림+테라코타 | 이 서비스의 팔레트(`tokens.css`) |
| 폰트 두세 개 섞기 | Pretendard 하나. 굵기와 크기로 위계를 만든다 |
| 모든 곳에 색 · 아무 데도 색 없음 | **색은 개념에 붙는다** — 분실 마리골드 = 잃어버림, 습득 코발트 = 주움. 두 색은 배지뿐 아니라 **면**(의도 선택 · 포스터 · 등록 권유)으로 크게 쓴다. 나머지(글자 · 선 · 공통 버튼)는 중성 잉크와 흰 종이. 빨강은 "멈춰서 볼 것"(오류 · 되돌릴 수 없는 동작 · 개인정보 · 안전 경고)에만(아래 "색의 뜻") |
| 아이콘 남발 · 직접 그린 아이콘 | 텍스트로 충분하면 텍스트. 아이콘은 Phosphor 한 벌 · 한 굵기 · 크기 토큰 |

**여백이 가장 싸고 효과적인 도구다.** 요소를 더 넣기 전에 간격부터 조정한다.

### 반경 — 네 단계 (2026-09-26)

크기가 아니라 **무엇인가**로 고른다. 이 밖의 값(2px, 14px …)을 쓰지 않는다. 규칙은 `tokens.css` 주석에도 있다.

| 토큰 | 값 | 쓰는 곳 |
|---|---|---|
| `--radius-xs` | 4px | 글자에 붙는 조각 — 배지(이름표) · 스켈레톤 글자 줄 · 포커스 링 · 이름표(툴팁) |
| `--radius-sm` | 8px | 누르는 것 — 버튼 · 입력 · 검색창 · 선택 칸 · 메뉴 항목 · 페이지 번호 |
| `--radius-md` | 12px | 놓이는 면 — 사진 · 포스터 · 색 면(의도 선택 · 다음 행동) · 상태 상자 · 시트 · 드롭다운 · 목록 카드 윤곽(안의 사진은 위 두 모서리만 12 − 3 = 9px, 2026-10-08) |
| `--radius-pill` | 999px | 조건을 켜고 끄는 것 — 필터 칩, 그리고 동그란 아이콘 버튼 |

배지(4px 이름표)와 칩(알약)이 모양으로 갈린다 — 하나는 정보, 하나는 조작이다.

### 아이콘 — Phosphor 한 벌

- `@phosphor-icons/react`만 쓴다. 굵기 `bold` 하나(`IconProvider`가 앱 전체에 준다). **직접 그리지 않는다**
- 크기는 `--icon-xs` 14 · `--icon-sm` 16 · `--icon-md` 20 · `--icon-lg` 24 · `--icon-state` 48. 옆 글자에 맞춘다
- 기본이 장식이다(`aria-hidden`). 아이콘만 있는 버튼 · 링크에는 `aria-label`과 이름표(툴팁 — 마우스 · 키보드에서만 뜬다)
- 새 아이콘은 `shared/ui/icons.tsx`의 목록에 더한다. 화면마다 다른 모양이 섞이지 않게
- 예외 둘 — 로고(꼬리표 두 장)는 서비스의 표지라 직접 그렸고(헤더 · 로그인 · 가입 머리 · 파비콘, `app/layouts/BrandMark`), 포스터 그림은 본인이 고른 삽화다
- **문구 안의 글자 기호를 아이콘처럼 쓰지 않는다**(2026-10-03 회의, `impeccable` 금지 항목 · 보안 결정 조건 13) — `↓` · `→` · `✓` · `※` 같은 글자는 Phosphor 아이콘(`CaretDown` · `Check` · `CheckCircle` · `Info` · `Eye` …)으로 바꾼다. 글자 기호는 글꼴마다 모양 · 크기가 달라 줄이 흔들리고, 사용자가 칠 수 있는 글자라 시스템 표시와 갈리지 않는다(남은 문서 그림의 `(v)` · `[✓ …]`는 설명용 표기다)

### 색의 뜻 — 빨강 (2026-10-03 회의 ⑤ · 개인정보 · 안전 경고 2026-10-07)

> **빨강 = 멈춰서 볼 것** — 방금 틀린 것(오류 문장 · `!` 아이콘)과 되돌릴 수 없는 동작(삭제), 그리고 **개인정보 · 안전 경고**(본인 피드백 2026-10-07).
> **빨간 채움은 되돌릴 수 없는 확인 버튼만**(`[삭제하기]`, `Button variant="danger"`). **상태 · 배지 · 면에는 빨강을 쓰지 않는다.**

> **개인정보 · 안전 경고(본인 피드백 2026-10-07)** — "전화번호 · 집 주소를 적으면 누구나 봐요." 같은 경고를 더 강조해 빨간색으로. 회의 ⑤의 "개인정보 · 경고에는 빨강 금지"를 이 자리만 바꿨다.
> 쓰는 것은 하나 — `shared/ui/SafetyNote`(글자 `--error-text` + 경고 세모 `Warning`, 굵기 600 · 카드 · 지갑 사진 줄은 700). 오류와 **모양으로 갈린다** : 오류는 동그라미 `!`(`WarningCircle`)이고 칸이 틀렸을 때만 뜨며 칸 테두리가 두 겹이 된다. 경고는 세모이고 **막지 않는다**(칸을 틀린 칸처럼 칠하지 않고 `role="alert"`도 두지 않는다). 색만으로 알리지 않는다 — 세모가 늘 함께 있다. 문장은 짧게(한 줄)

| 자리 | 쓰는 것 | 쓰지 않는 것 |
|---|---|---|
| 방금 틀린 칸 | 오류 문장 + `!` 아이콘(`WarningCircle`)의 글자색 `--error-text`(밝게 `#A62018` · 어둡게 `#FF8F85`, 둘 다 종이 위 7:1 이상) | 칸 테두리 · 칸 면을 빨갛게 — 테두리는 잉크 두 겹(`--selected-line`) 그대로 |
| 되돌릴 수 없는 동작 | 확인 창의 `[삭제하기]` 빨간 채움, 여는 `[삭제]` · `[사진 전부 삭제]`는 선 + 빨간 글자(`dangerQuiet`), 댓글 인라인 삭제 확인 칸의 옅은 빨강 면 | `[완료로 바꾸기]` — 되돌릴 수 없지만 파괴가 아니다(잃는 것이 없다). 잉크 |
| **개인정보 · 안전 경고** — 설명 칸 개인정보 줄 · 사진 속 개인정보 줄 · 연락처 감지 줄(글 폼 · 댓글 · 댓글 수정) · 연락중으로 바꾼 직후 안내(사칭 · 선입금) | 빨간 글자 + 경고 세모(`SafetyNote`). 종이 위 7.4 · 8.0, 옅은 면 위 6.7 · 7.1(`tokens.test.ts`) | 빨간 면 · 테두리 · 채움, 동그라미 `!`, 칸을 틀린 칸처럼 칠하기, 보내기를 막기 |
| 다른 창 로그아웃 · 결과 고지 · 쓰는 요령 · 도움말 | 굵은 잉크 글자 + 뜻을 말하는 아이콘(자물쇠 · 정보) | 빨강 — 틀린 것도, 개인정보 · 안전 경고도 아니라 알아 둘 것이다 |
| 배지 · 면 · 상태 | 개념 색(마리골드 · 코발트) · 잉크 | 빨강 |

- 적색약에게는 빨강이 종이 위 1.74:1로만 갈린다(회의 사용자 담당 계산). 그래서 오류를 지키는 것은 색이 아니라 **아이콘 · 문장 · 도움말 숨김**이다 — 오류가 떠 있는 동안 그 칸의 도움말은 숨겨 칸 아래에는 오류 한 줄만 남는다(결과 고지 줄은 남는다)
- 칸마다 붙은 `role="alert"`는 제출이 막혔을 때 한꺼번에 울리지 않게 한다 — 칸을 벗어나며 생긴 오류 하나만 바로 읽고, 제출이 막히면 포커스가 간 첫 칸이 읽는다(UI2-9)

### 선택 표시 — 무엇을 고르는지로 모양을 정한다 (2026-10-03 회의 ⑤-a)

| 고르는 것 | 표시 | 쓰는 곳 |
|---|---|---|
| 하나만 고르기 | **채운 점**(둥근 고리, 고른 것만 가운데가 찬다) | 등록 유형 두 칸 · 날짜 `[오늘]` `[어제]` · 목록 카테고리 · 상태 메뉴 |
| 여러 개 고르기 | **네모 체크** | (지금은 없다 — 생기면 이 모양) |
| 그림 칸 | **선 두 겹 + 접힌 귀퉁이**(모서리 표시) | 등록 종류 다섯 칸(오른쪽 위) · 설정 화면 모드 두 칸(이름 줄 끝 — 미리보기 그림과 겹치지 않게). 화면 모드에서 기기 설정을 따르는 중이면 **빈 테** 귀퉁이 + `기기 설정` 이름표, 고정하면 채운 귀퉁이 |
| 탭(주소가 바뀌는 묶음) | **밑줄**(글자 굵게 + 잉크 막대) | 내가 쓴 글 상태 탭 |
| 의도 | **색 면 + `[×]`** | 목록 의도 두 칸 |
| 두 칸 스위치 | 누른 칸을 잉크로 채움 | 내 글 관리 게시중 \| 연락중 |

- **동그라미 ✓는 "완료" 표시 전용이다**(완료 배지 · 완료 글 한 줄). 선택에 쓰면 "끝났다"와 겹친다
- 글자 선택지를 잉크로 채우는 안은 쓰지 않는다 — 기본값 "전체"가 가장 진해진다
- 색만으로 고른 것을 알리지 않는다. 위 모양이 늘 같이 있다

> **"색은 유형 배지에만" 규칙은 폐기했다(2026-09-25).** 1차 목록이 회청 잉크와 회색 캔버스뿐이어서 딱딱하고 칙칙했고,
> 분실/습득 구분이 작은 배지로 밀려 서비스가 데이터 조회 도구처럼 보였다. 절제는 "색을 없애는 것"이 아니라
> "색이 개념마다 한 곳에 모이는 것"이다. 크게 칠하는 곳은 첫 화면의 분실 · 습득 칸 한 곳이고, 나머지는 조용하다.
> 칸의 색은 그 칸이 보여 주는 글의 이름표 색과 같다(본인 2026-10-07) — 주황 칸을 누르면 주황 이름표(분실)의 글만 나온다.

## 2. 가독성 — 한글은 영문과 다르다

- **`word-break: keep-all`** — 한글 단어가 중간에서 끊기면 읽는 속도가 눈에 띄게 떨어진다
- **행간 1.7** — 영문 권장치(1.5)보다 넉넉해야 한다. 한글은 글자가 빽빽하다
- **본문 16px 하한** — iOS Safari는 16px 미만 입력 필드에 자동 확대를 건다. 화면이 갑자기 튄다
- **한 줄 45~75자** — 넘으면 다음 줄 첫 글자를 찾기 어렵다. 본문 컨테이너에 `max-width`를 둔다
- **대비** — 본문 4.5:1, 큰 글씨 3:1 (WCAG AA). 눈대중 말고 계산한다
- **회색 글씨를 남발하지 않는다.** 보조 정보라고 다 흐리게 하면 화면 전체가 흐릿해진다

### 숫자와 날짜

- 날짜는 `2026. 9. 23.`처럼 **자리를 고정**한다. 목록에서 세로로 안 맞으면 스캔이 깨진다
- 상대 시간("3일 전")은 7일까지만. 그 뒤엔 절대 날짜가 낫다
- 조회수 같은 숫자는 `tabular-nums`로 폭을 고정한다

## 3. 사용자 우선 — 시스템이 아니라 사람 기준으로 쓴다

### 문구는 사용자의 말로

| 시스템 말투 | 사용자 말투 |
|---|---|
| "게시글이 존재하지 않습니다" | "삭제되었거나 없는 게시글이에요" |
| "유효하지 않은 요청" | "제목을 입력해 주세요" |
| "처리 중" | "사진 올리는 중… (2/5)" |

**서버가 알려 주는 오류 문구는 프론트가 짓지 않는다.** 백엔드 `ErrorCode`가 이미 한글 문장을 갖고 있다(합니다체, 바꾸려면 백엔드). 프론트가 직접 쓰는 건 **빈 상태 · 확인 다이얼로그 · 결과 고지 · 도움말 · 보내기 전 검사 · 연결 실패**이고, 전부 **해요체**다(2026-10-03 회의 ⑦ — `"제목을 적어 주세요"` · `"댓글은 300자까지 쓸 수 있어요"` · `"연결하지 못했어요. 네트워크를 확인하고 다시 시도해 주세요."`). 보내기 전 검사 문장도 서버 문장처럼 **칸 이름으로 시작**한다(`이메일` · `비밀번호` · `닉네임` — 서버 문장의 첫 낱말로 칸을 가리는 규칙과 같다)

### 막다른 길을 만들지 않는다

모든 오류 화면에는 **나갈 문**이 있어야 한다.

- 404 → "목록으로 돌아가기"
- 네트워크 오류 → "다시 시도"
- 403 → 왜 안 되는지 + 다음에 할 일

### 사용자가 한 일을 잃게 하지 않는다

- 폼 제출이 실패해도 **입력값을 지우지 않는다**
- 작성 중 이탈은 **쓰던 칸 등록부** 하나로 확인한다(`shared/lib/dirtyRegistry` — 막는 곳은 레이아웃에 하나, 칸은 "쓰던 글자 있음"만 알린다. 화면정의서 1.7). 로그아웃 확인 · 다른 창 로그아웃도 같은 판정을 읽는다
- 로그인이 필요해 튕겨냈다면, 로그인 후 **원래 가려던 곳으로** 돌려보낸다

## 4. 체감 속도 — 실제 속도보다 중요하다

| 대기 시간 | 사용자 인지 | 필요한 처리 |
|---|---|---|
| ~100ms | 즉시 | 없음 |
| ~300ms | 살짝 느림 | 버튼 눌린 상태 |
| ~1초 | 기다리는 중 | 스켈레톤 |
| 1초 이상 | 멈춘 것 같음 | 진행률 또는 단계 안내 |

- **스켈레톤 > 스피너.** 스피너는 "얼마나 걸릴지 모름"을 뜻하고, 스켈레톤은 **레이아웃을 미리 잡아** 화면이 튀지 않게 한다
- **기다림 표시는 점 셋 하나다**(`shared/ui/LoadingDots`). 본인 요청(2026-10-14) — "입력 중" 점처럼 로딩이 짧게 느껴지게, 로딩이 걸리는 곳에 점 셋. 쓰는 곳을 셋으로 가른 것은 개발팀 판단이었고, 첫 로딩 자리는 QA 6차 뒤 **본인 결정(2026-10-14, QA-P-5)** 으로 정했다
  - **처음 불러오는 화면** = **스켈레톤 그대로 + 목록은 결과 제목 줄의 건수 자리에 점 셋**(본인 결정 2026-10-14). 카드 · 칸이 들어올 자리를 스켈레톤이 미리 잡아 응답이 와도 카드가 밀리지 않는다. 건수 자리는 2.75rem을 먼저 잡아 두어 점이 생겨도 줄이 밀리지 않는다(실측 375 · 1280 : 점이 생기기 전후 줄 · 첫 카드 자리 같음). 점 셋만 두면 빈 화면 한가운데 점만 있다가 응답과 함께 화면 전체가 새로 생긴다 — 더 느려 보인다. (남은 것 : 건수가 들어오면 칸이 2.75rem → 글자 폭으로 줄어 `이름표 안내`가 옆으로 약 19px 당겨진다 — 스켈레톤 때부터 있던 것)
  - **보던 내용이 있는 다시 받기**(목록 조건 바꿈 · 내가 쓴 글 탭 · 쪽) = 직전 내용을 흐리게 두고 **결과 줄 건수 바로 뒤에 점 셋**(목록 : 건수 뒤 · 이름표 안내 앞, 내가 쓴 글 : 탭 줄 바로 뒤). **흐름 안에 선다** — 카드 이름표 · 건수 · 이름표 안내를 덮지 않는다(QA-D-6, 예전엔 떠 있어 내가 쓴 글 카드 이름표 줄을 덮었다). 자리가 없으면(320 · 글자 200%) 다음 줄로. 누름을 받지 않는다(`pointer-events: none`)
  - **검색 추천** = 요청이 0.3초를 넘으면 **검색칸 안 지우기 `[X]` 바로 왼쪽에 점 셋**(찾는 말이 바뀌면 0.3초를 새로 센다, QA-D-4). 추천 칸 안에 줄을 더하지 않아 칸 높이가 결과 수로만 바뀐다. 결과는 치는 순간 앞 결과를 지금 말로 걸러 먼저 보인다(화면정의서 SCR-01 ②)
  - **누른 버튼의 요청**(로그인 · 가입 · 저장 · 비밀번호 바꾸기 · 댓글 · 올리기 · 삭제하기 · 완료로 바꾸기 · 더 보기 · 다시 시도 · 로그아웃) = **버튼 글자 자리의 점 셋**(`Button pending`). 글자는 자리만 남겨 버튼 크기가 그대로, 누름 · 제출은 무시(두 번 누름 방지). 이름은 처음부터 `가입하는 중` 같은 말로 읽힌다(이름에 `…`를 붙이지 않는다). 글 폼의 단계 줄(`사진 줄이는 중 → 올리는 중`)에는 점을 두지 않는다 — 점은 버튼 하나(QA-D-8). 계정 메뉴 로그아웃 · 내 글 상태 바꾸기 안내 줄은 글자 뒤 점 셋
  - **0.3초 안에 끝나면 아무것도 바뀌지 않는다**(`useLateFlag`) — 빠른 응답에 점이 한 번 깜빡이는 것이 가장 느려 보인다. **한 번 나타나면 적어도 0.45초 둔다**(QA-D-2 — 0.32 · 0.35초 응답에서 글자가 23 ~ 193ms만 사라졌다 돌아왔다). 버튼 안 점은 페이드 없이 글자와 같은 그림에서 바뀐다(빈 버튼 프레임 0). 따로 서는 점의 면만 200ms 옅게 나타난다
  - 색 : 버튼 안은 버튼 글자색(잉크 채움 위 흰 점), 따로 서는 점은 본문 잉크(`--text-body`, 면은 `--surface-sunken`). 새 색 없음. 움직임은 투명도 하나(1.2초 한 바퀴, 차례로) — 튀지 · 커지지 않는다. **가장 옅을 때도 바탕과 3:1**(투명도 하한 0.6 — 밝게 옅은 면 3.11 · 종이 3.23 · 어둡게 4.28 · 4.57 · 버튼 6.9 · 4.13, QA-D-5. 예전 0.3은 1.49 · 1.71). **모션 줄이기면 정지**(0.6 · 0.8 · 1). **강제 색상(고대비)** 에서는 점만 색 강제를 빼 CanvasText · ButtonText로 칠한다(예전엔 바탕색으로 바뀌어 버튼이 빈칸이 됐다, QA-D-3)
  - 알림은 `role="status"` · `polite`로 한 번(버튼 안은 이름이, 검색 추천은 기존 알림 줄 `찾는 중이에요.`가 맡는다 — 같은 말을 두 번 읽지 않게)
  - 모양(지금 말풍선 면 vs 점만)은 본인이 비교 캡처를 보고 고른다(QA-D-9, `round6\dots_compare_*`) — 고르기 전에는 지금 모양 그대로
- 이미지에는 `width`/`height` 또는 `aspect-ratio`를 지정한다. 없으면 로드될 때마다 아래 내용이 밀린다
- 이미지 업로드는 **몇 장 중 몇 장째인지** 보여준다. 5장이면 수 초가 걸린다
- 목록 이미지는 `loading="lazy"`

## 5. 일관성 — 같은 것은 같게

사용자는 규칙을 배운다. 규칙이 흔들리면 매번 다시 배워야 한다.

- 같은 동작은 **항상 같은 자리**. 목록 카드의 배지 위치가 화면마다 다르면 안 된다
- 주 동작 버튼은 항상 같은 스타일·같은 정렬
- 간격은 토큰에서만 가져온다. `margin: 13px` 같은 값이 나오면 토큰이 부족한 것이지 예외가 필요한 게 아니다
- 같은 데이터는 같은 형식으로. 목록의 날짜와 상세의 날짜가 다르면 안 된다

### 칸 크기 — 할 일의 무게로 세 단계 (2026-10-11)

> 본인 : 로그인 · 가입(56px)과 다른 화면(44px)의 크기가 갈려, 칸이 일곱 개인 글 폼이 오히려 더 작았다. "지금 디자인을 해치지 않는 더 나은 방향"

| 단계 | 칸 높이 · 칸 이름 | 주 버튼 | 쓰는 곳 | 근거 |
|---|---|---|---|---|
| 기본 | 44px(`--tap-min`) · 14px | 44px · 14px | 검색창(넓은 화면) · 필터 칸 · 댓글 · 확인 창 · 그 밖 | 읽는 화면 안의 작은 입력. 누르는 면 하한 |
| **쓰는 화면** | **48px(`--form-control-h`) · 16px** | **48px · 16px**(`[취소]`도 같은 줄이라 48px) | 글 등록 · 수정(SCR-02 · 04) · 설정(닉네임 · 비밀번호, SCR-08) | 화면의 일이 "써서 보내기"다. 칸이 일곱 개라 56px이면 폼이 길어지고(375 기준 약 +70px) 한 화면에 보이는 칸이 준다 — 한 단계만 |
| 할 일이 폼 하나 | 56px · 16px(입력 글자 18px) | 56px · 18px | 로그인 · 가입(SCR-05 · 06, `AuthLayout`) | 화면에 폼 하나뿐 — 크게 |

- 구현은 조상 변수 하나 — 틀(`PostForm`의 `.form` · 설정 `.page` · `AuthLayout`)이 `--field-h` · `--field-label-text`를 두고 `TextField` · `TextArea` · 고르는 칸 이름(유형 · 종류 · 사진)이 읽는다. 변수가 없으면 기본 단계다. 자리표시(글 폼 · 설정 스켈레톤)도 같은 높이를 쓴다(불러온 뒤 칸이 튀지 않게)
- **붙는 것 총량은 그대로** — 휴대폰 제출 줄은 위 여백을 12 → 8px로 줄여 버튼 48px에도 줄 높이 **69px**(선 1 + 8 + 48 + 12)를 지킨다. 헤더 57 + 69 = 126px ≤ 640px의 20%(8장). 이번에 잰 바탕 값 — 예전 줄은 81px이었다(빈 "남은 칸 수" 줄을 −12px 여백으로 접으려 했지만 격자 칸 높이는 음수가 되지 않아 12px이 늘 남았다). 빈 줄은 이제 흐름에서 뺀다(알림 영역으로는 남는다)
- 실측(비로그인 → 로그인 글 등록, 밝게) — 글 폼 높이 375×667 **1,390 → 1,409px**(+19) · 1280×800 **1,365 → 1,388px**(+23), 붙는 줄 81 → 69px, 넓은 화면 제자리 줄 76 → 68px. 칸 44 → 48px · 칸 이름 14 → 16px · `[올리기]` · `[취소]` 44 → 48px · 16px. 설정 칸 · `[저장]` · `[비밀번호 바꾸기]` 48px. 320 · 375 · 1280에서 `scrollWidth = clientWidth`. 남은 칸 수 줄이 뜬 상태(제출이 막힘)의 붙는 줄 100px — 예전과 같다(→ 16px로 올린 뒤 104px, 아래)
- **쓰는 화면의 칸 오류 · 남은 칸 수 줄은 16px**(본인 결정 2026-10-11, QA D-13) — 칸 이름이 16px인데 그 아래 오류가 14px, 제출 줄 위 `"5곳을 더 채워야 올라가요"`가 13px이라 "여기가 막혔다"가 이름보다 작게 말했다. 틀(`PostForm`의 `.form` · 설정 `.page`)이 `--field-error-text: var(--text-base)`를 두고 `TextField` · `TextArea` · 유형 · 종류 · 사진 칸의 오류가 읽는다(아이콘은 첫 줄 가운데 `(1lh − 16px) / 2`). 도움말(회색)은 14px 그대로 — 오류보다 한 단계 아래. 남은 칸 수 줄은 16px/700 잉크. 댓글 칸 · 목록 필터 · 내 글 관리의 오류는 기본(14px) 그대로
  - 실측(로그인, 빈 [올리기]) — 칸 오류 다섯 줄 14 → **16px**, 남은 칸 수 줄 13 → **16px**(높이 19 → 23px), 줄 아래 끝 ~ `[올리기]` 12px 그대로. 막힌 동안 붙는 줄 **100 → 104px**(8장 예외), 넓은 화면 제자리 줄 99 → 103px. 설정 비밀번호 빈 제출 오류 16px. 320 · 360 · 375 · 390 · 768 · 1280에서 `scrollWidth = clientWidth`
- 댓글 칸은 기본 단계로 둔다 — 읽는 화면(상세) 안의 한 칸이고, 휴대폰 하단 댓글 줄(붙는 줄)과 쓰는 칸이 같은 모양이라 함께 커지면 붙는 줄이 늘어난다

## 6. 모션 — 부드럽게 이어 주기 (2026-09-26 넓힘)

> 본인 : "AI 티는 나지 않으면서 자연스러운 애니메이션" · "너무 치장한다기보단 부드럽게 이어 주는 화면 느낌으로"

- **이유가 한 문장으로 설명되는 움직임은 넣는다** — 상태가 바뀜(선택 · 오류 · 안내가 나타남), 어디서 나왔는지(시트 · 메뉴), 불러오기 → 내용(사진이 떠오름), 화면 모드 전환(겹쳐 넘김), 눌림
- 짧은 페이드와 작은 이동(4~8px)이면 충분하다. **사용자가 움직임 자체를 알아채지 못해도 성공이다**
- 금지 : 무한 반복 장식 · 스크롤할 때마다 튀어 오르는 등장 · 패럴랙스 · 스크롤 가로채기 · 통통 튀는 스프링 · 줄줄이 순서대로 나타나기
- 지금 있는 전환 : 폼 오류 · 안내 · 잠금 안내(위에서 4px 내려오며 나타남 200ms) · 목록 사진(옅은 면 → 사진, 투명도 280ms) · 화면 모드(View Transitions 교차 280ms, 없는 브라우저는 바로) · 시트 · 계정 메뉴 · 목록 조건 바꿀 때 흐림 · 온보딩(테 투명도 · 넓은 화면 카드 6px 떠오름 · 좁은 화면은 글만 4px, 대상까지 부드러운 스크롤) · 이름표 안내 펼침(위에서 4px) · **상세(2026-09-27)** : 사진 넘기기(스크롤 스냅, 버튼 · ← → 는 부드러운 스크롤 — 모션 줄이기면 즉시) · 크게 보기 열림(투명도) · 확인 다이얼로그(6px 떠오름) · 방금 남긴 댓글(아래에서 4px) · 인라인 확인 칸(위에서 4px) · 짧은 알림(아래에서 6px, 280ms) · **등록 · 수정(2026-09-27)** : 유형 칸 면 색 바뀜(200ms) · 고른 칸 체크(투명도 + 살짝 커짐) · 고른 종류 그림이 6도 기울어짐 · 사진 칸 나타남(아래에서 4px) · 교체 · 삭제 안내 면(위에서 4px) · 제출 단계 줄(위에서 4px) · **내가 쓴 글 · 없는 화면(2026-09-27)** : 고른 탭의 아래 막대(투명도 + 가로로 살짝 펴짐, 200ms — 옮겨 가는 것처럼 보인다) · 탭을 바꾸는 동안 직전 글 흐림 · 빈 상태 면 나타남(투명도) · 없는 화면 면(아래에서 4px) · 쓰던 댓글 묻는 칸(위에서 4px) · 그 칸까지 부드러운 스크롤 · **디자인 회의 반영(2026-10-04)** : 휴대폰 하단 댓글 줄(아래에서 줄 높이만큼 미끄러져 들어옴 200ms, 나갈 때 120ms — 떠 있어 레이아웃을 밀지 않는다) · 댓글 입구를 누르면 쓰는 칸까지 부드러운 스크롤 · 연락처 감지 줄 · 다른 창 로그아웃 줄(위에서 4px, `appear`) · 칩 아래 펼침 칸 · 종류 칸 귀퉁이(나타남) · 화면 모드 귀퉁이(투명도만) · [더 보기]로 붙은 카드는 움직이지 않는다(이미 본 카드는 제자리 — 흐림도 없다)
- **기다림의 점 셋(2026-10-14)** : 0.3초 넘게 기다릴 때만 나타나(따로 서는 면만 200ms 옅게) 점 셋이 차례로 짙어졌다 옅어진다(투명도 0.6 ↔ 1, 1.2초). 한 번 나타나면 0.45초 이상. 로딩 표시는 기능이라 반복하지만 장식 반복은 여전히 금지다. 모션 줄이기면 멈춘 점 셋(4장)
- **눌림은 한 가지다** — 누를 수 있는 모든 것(버튼 · 링크 · 칩 · 의도 칸 · 카드 · 선택 칸)이 잠깐 옅어진다(`--press-opacity` 0.72). 크기 · 위치를 바꾸지 않아 옆 요소가 흔들리지 않는다. `global.css`의 선택자 무게 0 규칙 하나가 준다
- 모바일의 회색 탭 하이라이트는 모든 요소에서 똑같이 끈다(`reset.css`). 대신 위의 눌림이 반응한다
- 120 · 200 · 280ms(`--duration-fast` · `base` · `slow`). 면 전체가 바뀌는 것만 280ms, 길면 느리게 느껴진다
- `ease-out`(들어올 때) / `ease-in`(나갈 때)
- **레이아웃을 흔드는 애니메이션 금지.** `transform`과 `opacity`만 쓴다
- `prefers-reduced-motion: reduce`를 반드시 존중한다. 전정기관 질환이 있는 사용자에게는 어지럼증을 유발한다

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    transition-duration: 0.01ms !important;
  }
}
```

## 7. 접근성 — 최소선이 아니라 기본

- 모든 폼 입력에 `label` (`placeholder`는 label이 아니다 — 입력하면 사라진다)
- **색만으로 정보를 전달하지 않는다.** 배지는 색 + 텍스트, 오류는 색 + 아이콘 + 문장
- 포커스 링을 지우지 않는다. 디자인이 맘에 안 들면 다시 그리되 없애지 않는다
- 터치 대상 최소 44×44
- 이미지 `alt`는 "이미지"가 아니라 내용. 장식용이면 `alt=""`
- 본문 바로가기 링크(skip link)
- 동적으로 바뀌는 영역에 `aria-live` — 검색 결과 개수 같은 것. **뜰 때만 나타나는 줄(연락처 감지 줄 등)은 비어 있어도 알림 영역으로 늘 둔다** — 영역이 글자와 함께 생기면 스크린리더가 처음 한 번을 놓친다
- **알림은 한 번만** — 칸을 벗어나며 생긴 오류 하나는 바로 읽고(`role="alert"`), 제출이 막혀 여러 칸에 한꺼번에 붙은 오류는 읽지 않는다. 포커스가 간 첫 칸이 `aria-describedby`로 읽고, 남은 수는 한 줄(`"3곳을 더 채워야 올라가요"`)이 알린다(회의 UI2-9)
- **위험 동작은 자주 쓰는 동작과 16px 떼고 모양도 다르게**(회의 RV-3 · ⑦) — 상세 `[수정]`–`[삭제]` · 댓글 `[수정]`–`[삭제]` · 댓글 삭제 확인 `[취소]`–`[삭제하기]`. 자리 · 순서는 그대로 둔다 — `[삭제]`를 줄 끝으로 옮기면 확인 창의 `[삭제하기]` 자리와 겹쳐 두 번 누름이 통과한다. 막 나타난 확인 버튼은 0.5초 안에 시작된 누름을 받지 않는다(보안명세서 SE-1)
- **전수 점검(2026-10-14)** — 40개 화면 상태 × 375 · 1280에서 실제 누르는 면(hit-test) · 이름 · 이름표 · Tab · Esc/바깥 누름 · 글자 200%를 쟀다. 고친 것 : 날짜 칸 어디를 눌러도 달력(`openDatePicker`) · 검색 Esc가 글자를 지우던 것 · 고른 의도 칸 전체로 처음 목록 · **좁은 폭 헤더 로고의 누르는 면 30 → 44px**(::after, 모양 그대로) · **라디오 묶음(글 종류 · 물건 종류)의 오류를 라디오에도 잇기**(`aria-describedby` — 묶음 설명을 라디오 포커스 때 읽지 않는 낭독기가 있다). 사진 크게 보기는 바깥이 곧 사진이라 바깥 누름으로 닫지 않는다(닫기 · Esc · 뒤로가기)
- 붙는 줄(칩 줄 · 제출 줄 · 하단 댓글 줄)이 포커스를 가리지 않게 `scroll-padding-top` · `scroll-padding-bottom`을 **줄의 실제 높이**로 둔다(WCAG 2.4.11). 숨은 줄은 `inert`

## 8. 모바일이 기준 — 데스크톱은 넓어진 모바일

사용자는 **물건을 잃어버린 직후, 길에서** 이 서비스를 연다.

- 한 손 조작. 주 동작 버튼은 **엄지가 닿는 아래쪽**에
- 밝은 야외 — 대비가 낮으면 아예 안 보인다
- 느린 네트워크 — 이미지가 무거우면 목록이 안 뜬다
- 입력 타입을 정확히 — `type="email"`, `inputMode="numeric"`. 키보드가 바뀐다
- 하단 고정 요소는 `env(safe-area-inset-bottom)`을 고려한다

### 붙는 것 총량 규칙 (2026-10-03 회의)

> **한 화면에 붙는 것은 헤더 + 줄 하나까지. 둘째 줄은 화면 높이 `min-height: 40rem`에서만. 떠 있는 버튼도 하나로 센다.**

| 화면 | 붙는 줄 | 붙는 조건 |
|---|---|---|
| 목록 | 칩 줄(헤더 아래) | 높이 40rem 이상 · 폭 22.5rem 이상(320은 칩이 두 줄이라 안 붙는다). 검색칸은 붙지 않는다 |
| 상세 | 휴대폰 하단 댓글 줄 | 폭 48rem 미만 · 높이 40rem 이상. 흐름 안 입구가 위로 나간 뒤에만 나타나고 쓰는 칸이 보이면 숨는다 |
| 등록 · 수정 | 휴대폰 제출 줄 | 폭 48rem 미만 · 높이 40rem 이상. 40rem 미만은 폼 끝 제자리 |

- 기준 : 헤더 57 + 줄 69 = 126px가 화면 높이의 20% 이하가 되는 경계가 40rem이다(폼 제출 줄은 2026-10-11에야 실제로 69px이 됐다 — 5장 "칸 크기"). 짧은 화면 · 가로 모드 · 200% 확대에서는 줄이 본문을 가리는 몫이 커서 저절로 꺼진다
- **예외 하나 — 제출이 막힌 동안의 폼 제출 줄**(본인 결정 2026-10-11, QA D-14). 막히면 남은 칸 수 줄(`"5곳을 더 채워야 올라가요"`, 16px)이 `[올리기]` **바로 위**에 붙어 있어야 한다(근접성 — 무엇이 막혔는지가 누르려던 버튼 옆에 있다. 줄을 폼 위로 떼면 버튼을 누른 사람이 못 본다). 그래서 이 상태에서만 붙는 줄이 69 → **104px**이 되고, 헤더와 합쳐 화면 높이의 **약 24 ~ 25%** 를 덮는다. 칸을 다 채우면 줄이 사라져 69px로 돌아간다
  - 실측(2026-10-11, 칸 오류 · 남은 칸 수 16px 뒤) — 붙는 줄 104px : 360×640 **16.3%**(헤더 포함 161px = **25.2%**) · 375×667 **15.6%**(**24.1%**) · 390×844 12.3%(19.1%). 40rem 미만(320×568)과 48rem 이상(768 · 1280)은 붙지 않아 제자리 줄 103px. 16px로 올리기 전 100px — 360×640 15.6%(24.5%) · 375×667 15.0%(23.5%)
  - 이 예외를 늘리지 않는다 — 막힌 상태의 한 줄 말고는 붙는 줄에 무엇도 더하지 않는다. 붙는 줄은 `--form-bar-h`로 자기 높이를 재어 `scroll-padding-bottom`을 맞추므로(7장) 커진 동안에도 포커스한 칸을 가리지 않는다
- **떠 있는 버튼(FAB)은 두지 않는다** — 줄 하나로 센다. 글쓰기 입구는 헤더 `[+]`(보던 의도를 싣는다)와 흐름 안 링크가 맡는다(회의 ②)
- **짧은 알림(`Flash`)은 아래 붙은 줄 위로 비켜 뜬다** — 아래 붙은 줄이 `useBottomInset`으로 자기 높이를 `--bottom-inset`에 알리고(+ `scroll-padding-bottom`), 알림은 `max(기본 자리, --bottom-inset + 12px)`에 뜬다(API2-3). 4초 동안 줄의 버튼 글자를 가리지 않는다. 줄이 숨으면 0으로 돌린다. 지금 이 값을 알리는 줄은 상세 댓글 줄이다(폼 제출 줄은 `--form-bar-h`로 스크롤 여백만 잰다 — 폼에서는 짧은 알림이 뜨지 않는다)

## 9. 빈 상태를 설계한다

빈 화면은 **오류처럼 보인다.** 가장 자주 방치되고 가장 티가 나는 자리다.

| 상황 | 필요한 것 |
|---|---|
| 검색 결과 0건 | 왜 없는지 + 조건을 넓히는 방법(`[필터 모두 지우기]` · `[검색어 지우기]` — 칩 줄에는 한 번에 지우는 버튼이 없어 이것이 0건의 출구다, 본인 2026-10-07) + 그 아래 등록 권유 면 하나. **검색어 · 주소 값을 제목 문장에 넣지 않는다**(주소로 남의 화면에 문장을 심는 통로 — 검색칸에 이미 보인다). 회색 판을 깔지 않는다 |
| 첫 방문(글이 없음) | 무엇을 할 수 있는지 + 첫 행동 버튼(칸을 고르지 않았으면 `[분실 글 올리기]` `[습득 글 올리기]` 두 버튼 — 처음 목록 끝 면과 같다) |
| 내가 쓴 글 0건 | 권유. "아직 올린 글이 없어요" + 글쓰기 |
| 댓글 0건 | "아직 댓글이 없어요." + 글의 유형에 맞춘 한 줄("이 물건을 본 적 있다면 댓글로 알려 주세요.") |

## 10. 마이크로카피

- 버튼은 **동사**로. "확인"보다 "삭제하기", "등록하기"
- 다이얼로그 버튼은 **무슨 일이 일어나는지** 말한다. "예/아니오"보다 "삭제하기/취소"
- 부정문보다 긍정문. "취소하지 않으려면"보다 "계속 작성하려면" · "그대로 두려면 선택하지 마세요"보다 "지금 사진 N장이 그대로 남아요"(회의 RV-8)
- **프론트 문장은 해요체**(3장). 같은 묶음은 같은 뿌리의 말로 부른다 — 분실 글은 어디서나 "잃어버린 물건" · `분실 글`, 습득 글은 "주운 물건" · `습득 글`(카드 이름표와 같은 말), 같은 입구는 어디서나 같은 이름(`분실 글 올리기`, 회의 RV-9). **고르는 칸의 이름 = 그 칸이 보여 주는 글의 종류**다 — 고르는 말(내가 한 일)과 보여 주는 글을 엇갈리게 짓지 않는다(본인 2026-10-07, 예전 `물건을 잃어버렸어요` → 습득 글은 폐기)
- 당연한 도움말은 뺀다 — 칸 이름 · 칸 자체(`max`)가 이미 말하는 것을 한 줄 더 쓰지 않는다. 예시는 입력칸 안 안내 글로(이름은 늘 위에), 글자 수는 한도의 80%부터(회의 UI-9)
- 사과하지 않는다. "죄송합니다"보다 **무엇을 하면 되는지**

## 11. 반응형 — 기기가 아니라 내용이 기준

### 브레이크포인트는 내용이 깨지는 지점에서 끊는다

"아이폰 12는 390px"처럼 기기 이름으로 정하지 않는다. 기기는 계속 나온다. **레이아웃이 어색해지는 폭**에서 끊는다.

| 토큰 | 폭 | 이 지점에서 바뀌는 것 |
|---|---|---|
| (기본) | 320px~ | 목록 **정사각 사진 피드 2열**, 의도 선택 두 칸 나란히, 필터는 칩 하나 = 묶음 하나 → 작은 바텀 시트. 320(22.5rem 미만)은 칩 줄이 줄을 바꾼다 |
| 22.5rem | 360px | 칩 줄이 옆으로 넘기는 한 줄이 되고 헤더 아래에 붙을 수 있다(높이 40rem 이상). 360~374px 로고는 글자 14px · 꼬리표 26px |
| `--bp-md` | 768px | 목록 3열(목록 칸 34rem 이상), 사이드 여백 등장, **필터가 누른 칩 바로 아래 펼침 칸으로**(가운데 다이얼로그 아님). 휴대폰 하단 댓글 줄 · 붙는 제출 줄이 꺼진다. 상세는 한 줄 그대로(사진 상자만 4:3) |
| `--bp-lg` | 1024px | 목록 4열(목록 칸 54rem 이상), 검색창(44px)과 필터 칩이 한 줄에 선다(칩은 줄 가운데). **필터는 여전히 칩 → 펼침 칸**(옆 열 없음). **상세가 2단** — 왼쪽 사진 열(따라 내려옴) + 오른쪽 읽기 열 30rem(1280 이상 34rem) |
| `--bp-xl` | 1280px | 본문 최대폭 도달 |

목록 열 수는 화면 폭이 아니라 **목록 칸의 폭**으로 정한다(컨테이너 쿼리). 사진 없는 글도 포스터(유형 색 바탕 + 카테고리 그림)가 사진 자리를 채우므로 좁은 화면도 2열이다(2026-09-25 재설계. 1차의 모바일 1열 가로형 · 1024 이상 왼쪽 필터 열은 폐기)

**모바일 우선으로 쓴다.** 기본 스타일이 좁은 화면이고 `min-width`로 넓혀간다. `max-width`로 깎아내려가면 예외가 겹쳐 금방 엉킨다.

### 브레이크포인트 없이 되는 것부터 한다

미디어 쿼리는 마지막 수단이다. 대부분은 아래로 해결된다.

```css
/* 열 수를 자동으로 — 카드 최소 폭만 정하면 알아서 늘고 준다 */
grid-template-columns: repeat(auto-fill, minmax(280px, 1fr));

/* 유동 타이포 — 단계별 점프 없이 매끄럽게 */
font-size: clamp(1.5rem, 1.1rem + 2vw, 2.25rem);

/* 본문 줄길이 제한 — 큰 화면에서 한 줄이 120자가 되는 것을 막는다 */
max-width: 68ch;

/* 여백도 유동으로 */
padding-inline: clamp(1rem, 4vw, 3rem);
```

### 컨테이너 쿼리 — 컴포넌트가 스스로 판단한다

게시글 카드는 목록(3열)에도, 마이페이지(1열)에도, 사이드바에도 놓인다. **화면 폭이 아니라 자기가 놓인 자리의 폭**을 봐야 한다.

```css
.card-list { container: card-list / inline-size; }

@container card-list (width >= 380px) {
  .card { grid-template-columns: 96px 1fr; }  /* 썸네일 가로 배치 */
}
```

화면 폭으로 판단하면 "넓은 화면의 좁은 사이드바"에서 깨진다.

**그릇에는 이름을 붙이고, 질의는 늘 이름으로 잰다**(QA-D-21, 2026-10-13). 이름 없는 `@container (…)`는 "가장 가까운 조상 그릇"을 재고, 칸은 자기 자신의 그릇이 될 수 없다. 글 올리기 유형 칸이 자기 여백을 자기 폭으로 바꾸려던 규칙은 바깥 그릇이 없어 꺼져 있다가, 앱 전체를 감싸는 헤더 그릇(`shell`)이 생기자 글자 100%에서도 켜져 칸이 100 → 107px로 커졌다. 그래서 `container-type`만 쓰지 않고(`container: 이름 / inline-size`), 이름은 한 곳에서 짓고, `shell` 말고는 지은 파일 안에서만 잰다. 질의 안에서 그릇을 지은 칸 자신을 고치지 않는다. `src/shared/styles/containers.test.ts`가 넷을 다시 본다

### 터치와 마우스를 구분한다

```css
@media (hover: hover) {
  .card:hover { border-color: var(--ink-300); }
}
```

이 가드가 없으면 터치 기기에서 **hover 스타일이 탭 후에 들러붙는다.** 다른 곳을 누를 때까지 안 풀린다.

- 터치 대상 44×44 (마우스는 32로 줄여도 된다)
- 터치 기기에서는 hover로만 나타나는 정보를 두지 않는다. 수정·삭제 버튼을 hover로 감추면 모바일에서 영영 못 찾는다

### 높이도 반응형이다

- 가로 모드 휴대폰은 높이가 375px 남짓이다. `height: 100vh` 모달은 내용이 잘린다. `max-height: 90dvh` + 내부 스크롤
- `vh` 대신 **`dvh`** — 모바일 브라우저 주소창이 접히면 `vh`가 어긋난다
- 하단 고정 바는 `padding-bottom: env(safe-area-inset-bottom)`
- **붙는 줄은 높이로도 끈다** — 둘째로 붙는 줄(목록 칩 줄 · 상세 하단 줄 · 폼 제출 줄)은 `min-height: 40rem`에서만(8장 총량 규칙)

### 큰 화면에서 여백만 늘리지 않는다

1440px에서 콘텐츠가 가운데 720px만 차지하고 양옆이 텅 비면 성의 없어 보인다. **정보 밀도를 올린다** — 열을 늘리거나(목록 피드 4열), 목록과 상세를 2단으로.

### 확인해야 할 폭

```
320   가장 좁은 기기 (갤럭시 폴드 접힘)
375   기준
414   큰 휴대폰
768   태블릿 세로
1024  태블릿 가로 · 작은 노트북
1440  데스크톱
```

**320px에서 가로 스크롤이 없어야 한다.** 375만 보면 폴드에서 깨진다. 브라우저 확대 200%도 같이 본다 — 저시력 사용자의 실제 환경이고, 폭이 절반이 되는 것과 같다.

## 12. 디자인은 완료되지 않는다

**"동작한다"에서 멈추지 않는다.** 화면을 만든 뒤 반드시 다시 본다.

### 만든 직후 하는 것

1. **실제로 렌더링해서 본다.** 코드만 읽고 판단하지 않는다. 375 / 768 / 1440에서 각각
2. 0장 체크리스트를 처음부터 끝까지 짚는다
3. **스크린샷을 찍어서 본다.** 화면에서 볼 때와 이미지로 볼 때 눈에 띄는 게 다르다
4. `front-review` 에이전트로 검수한다

### 한 번 더 묻는다

- 이 화면에서 **뺄 수 있는 요소**가 있나? 더할 것보다 뺄 것을 먼저 찾는다
- 처음 보는 사람이 **3초 안에** 뭘 하는 화면인지 아나?
- 이 배치 말고 더 나은 배치가 있나? 첫 안을 그대로 쓰지 않는다
- 흑백으로 바꿔도 위계가 유지되나?
- 내용이 **2배로 길어져도** 안 깨지나? 제목 100자, 댓글 300자가 실제 상한이다
- 내용이 **비어 있어도** 멀쩡한가?

### 개선은 커밋으로 남긴다

디자인 개선도 기능만큼 커밋을 쪼갠다. `게시글 카드 정보 위계 조정` 처럼 **무엇을 왜 바꿨는지** 남으면, 나중에 되돌아갈 때 근거가 된다.

## 13. 어둡게 모드 — 사용자가 고른다 (2026-09-26)

- **고르는 곳** : 설정 화면(SCR-08)의 "밝게" · "어둡게" 두 칸. 고르지 않았으면 기기 설정을 따른다. 저장은 `localStorage` `theme:v1`
- **첫 화면 전에 적용한다** — `public/theme-init.js`가 `<html data-theme>`을 붙인다. 흰 화면이 한 번 번쩍이지 않는다
- **컴포넌트는 의미 토큰만 쓴다**(`--text-strong` · `--surface` · `--lost-face` …). 원값(`--ink-900` · `#fff`)을 직접 쓰지 않는다. 그래야 두 모드가 같은 코드로 그려진다
- 요소 하나에 `data-theme`을 붙이면 그 안은 그 모드로 그려진다(설정 화면의 미리보기)
