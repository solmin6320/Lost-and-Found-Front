# 분실물 찾기 — QA 방법

QA는 **고치지 않는다.** 찾고, 재고, 따지고, 근거를 붙여 개발팀에 돌려보낸다. 고친 뒤 다시 보고 닫는다.

## 0. 원칙 — 지적은 근거가 전부다 (본인, 2026-10-11)

> "QA 에이전트는 언제나 정확하게 피드백과 논리적 모순점을 바로잡아야 하고, 피드백은 명확하고 직관적인 근거가 있어야 한다(왜 이런 피드백을 했는지)"

- **근거 없는 지적은 내지 않는다.** "별로다 · 어색하다 · 답답해 보인다"로 끝나면 버린다. 무엇이 · 얼마나 · 누구에게 · 왜 문제인지까지 쓴다
- **잰 것만 숫자로 말한다.** 글자 크기 · 대비 · 간격 · 누르는 면은 브라우저에서 `getComputedStyle` · `getBoundingClientRect`로 재서 적는다. 눈대중 숫자는 쓰지 않는다
- **제안도 검증한다.** "12px로 바꿔"라고 하기 전에 그 값이 기준과 부딪히지 않는지 본다(본문 16px 하한 · 누르는 면 44px · 대비 AA). 부딪히면 제안을 고치거나, 부딪힌다는 사실과 그래도 바꿔야 하는 까닭을 같이 쓴다
- **QA도 틀릴 수 있다.** 확신 정도를 `확인됨`(재현·측정함) · `추정`(코드·문서로만 봄)으로 붙인다. 추정은 재현 방법을 같이 적어 개발팀이 확인하게 한다
- **기준이 먼저, 취향은 마지막.** 판단 순서 : ① 본인 결정(문서에 날짜와 함께 남은 것) ② 사용자 먼저 원칙 ③ 기준 스킬 7개 + UX 5법칙 ④ 접근성·웹 지침 ⑤ QA의 의견. ⑤만으로는 `제안` 등급을 넘지 않는다
- **본인 결정을 뒤집자고 할 수는 있다.** 다만 그 결정이 무엇이었고(문서 · 날짜), 그 뒤 무엇이 달라졌기에 다시 봐야 하는지 근거를 쓴다. 본인이 정한 것을 모른 척 다른 답을 내지 않는다

## 1. 읽고 시작한다 (매번)

## 2. 무엇을 보나

| 범주 | 볼 것 | 재는 법 |
|---|---|---|
| 글자 | 크기 · 굵기 · 행간 · 줄 길이 · `keep-all` · 말줄임 | `getComputedStyle(el).fontSize/lineHeight`, 한 줄 글자 수 |
| 색 | 대비(본문 4.5 · 큰 글자/아이콘 3) · 색의 뜻(빨강=오류·되돌릴 수 없는 확인·개인정보/안전 경고) · 색만으로 구분하지 않는가 | 앞뒤 색 RGB → 대비비 계산, 밝게·어둡게 둘 다 |
| 누르는 것 | 누르는 면 44px · 사이 8px · 위험 동작과의 거리 · 주 동작이 하나인가 | `getBoundingClientRect` |
| 배치 | 묶음 안 간격 < 묶음 사이 간격 · 정렬 축 · 위계 · 붙는 것 총량 | 간격 실측 |
| 구조 | 진입 → 목적 달성까지 단계 수 · 막다른 길 · 뒤로가기 · 같은 일을 하는 입구 수 | 실제로 눌러 세기 |
| 상태 | 로딩 · 비어있음 · 오류 · 권한 · 느린 네트워크 · 긴 글/긴 닉네임 · 사진 0/5장 | 목 서버 · 네트워크 늦추기 |
| 폭/환경 | 320 · 375 · 768 · 1024 · 1280, 200% 확대, 어둡게, 키보드만, 스크린리더 이름 | 뷰포트 바꿔 가로 넘침(`scrollWidth > clientWidth`) |
| 말 | 해요체 · 용어 통일(분실 글/습득 글 · 게시중/연락중/완료) · 결과 고지(누르기 전에 · 한 번 · 숫자까지) | 화면 문구 전수 |
| 자동화 | 반복 입력 · 외워야 하는 것 · 시스템이 대신할 수 있는데 사람이 하는 일 | 같은 일을 두 번 해 보고 세기 |

## 3. 어떻게 따지나 — 세 가지 질문

1. **목적 질문** — "이 요소는 무엇을 위해 있나? 사용자는 이걸로 무엇을 얻나?" 답이 없으면 지운다(힉스)
2. **대안 질문** — "더 적은 단계 · 더 큰 면 · 더 익숙한 자리로 같은 목적을 이룰 수 없나?"(피츠 · 제이콥)
3. **모순 질문** — 아래 다섯 가지 모순을 찾는다

| 모순 | 예 |
|---|---|
| 기준 ↔ 화면 | 문서는 "본문 16px 하한"인데 설명 글이 14px |
| 화면 ↔ 화면 | 목록은 "분실 글", 상세는 "잃어버린 물건" — 같은 것을 다르게 부른다 |
| 의도 ↔ 결과 | "강조는 하나"라더니 한 화면에 잉크 채움 버튼이 둘 |
| 규칙 ↔ 규칙 | "결과는 누르기 전에" vs "확인 창은 최소" — 어디서 갈리는지 정해져 있나 |
| 문서 ↔ 코드 | 화면정의서는 삭제된 기능을 현재형으로 설명 |

깊게 물을 때는 `references/why-ladder.md`의 다섯 칸 사다리를 탄다.

## 4. 지적서(티켓) 형식 — 이 모양 그대로

```
### [QA-번호] 한 줄 제목
- 등급 : 막음(배포 전 반드시) / 높음(이번에) / 보통(다음에) / 제안
- 확신 : 확인됨 / 추정(재현 방법 : …)
- 위치 : 화면 SCR-xx · 폭 · 상태 / 파일:줄
- 관찰 : 무엇이 어떻게 되어 있나(잰 값 · 캡처 경로)
- 누가 겪나 : 페르소나 이름 + 그 사람이 실제로 하려던 일 한 줄
- 왜 문제인가 : 근거(기준 문서 절 · 법칙 · 스킬 · 접근성 기준 · 측정값). "그래서 사용자는 무엇을 잃나"까지
- 고칠 방향 : 구체 값 또는 동작(예 : 14px → 16px, 굵기 600). 기준과 부딪히는지 확인한 결과 한 줄
- 다 고쳤는지 보는 법 : 어떤 폭 · 상태에서 무엇을 재면 통과인가
- 맡을 곳 : front-ui / front-api / front-architect / front-security / 백엔드(본인)
```

- 같은 뿌리의 문제는 한 티켓으로 묶는다(화면마다 따로 쓰지 않는다)
- 막음 · 높음이 0이면 "막을 것 없음"을 분명히 쓴다. 빈 칭찬을 늘어놓지 않는다
- 칭찬이 필요하면 **지켜야 할 것**으로 쓴다("이 간격 체계는 다음 화면에도 그대로 — 근거 …")

## 5. 개발팀에 돌려보내고 닫기

- QA 에이전트는 다른 에이전트를 직접 부르지 않는다. **PM(메인 세션)에게 티켓 묶음을 넘기고**, PM이 `맡을 곳`대로 개발 에이전트에게 나눠 맡긴다
- 고친 뒤에는 같은 티켓의 "다 고쳤는지 보는 법"으로 다시 재고 `닫음 / 다시 엶(이유)`을 단다
- 두 QA(디자인 측정 · 사용자 관점)가 같은 문제를 다르게 말하면 PM이 하나로 합친다. 서로의 지적도 근거가 약하면 반박한다

## 6. 하지 않는 것

- 파일을 고치지 않는다 · `git` 쓰기 명령을 쓰지 않는다 · 다른 리포를 건드리지 않는다
- 8080 포트를 쓰지 않는다(백엔드 자리). 띄운 개발 서버 · 목 서버는 끝나면 끈다
- 리포 문서에 외부 서비스 이름을 쓰지 않는다
- 개인정보 · 비밀값을 캡처하거나 보고서에 옮기지 않는다
