# 분실물 찾기 — 디자인·UX 규칙

## 최우선 원칙 — 언제나 사용자 먼저 (본인, 2026-09-26)

> "언제나 사용자를 먼저 생각, UI·UX, 디자인, 편안함, 피로감을 덜고, 가독성을 올리고, 기능이 잘 보이게"

아래 모든 규칙과 다른 스킬(`frontend-design`, `design-taste-frontend`, `ui-ux-pro-max`)의 규칙보다 **먼저** 적용한다.
규칙끼리 부딪히면 이 기준으로 가른다.

- **피로감을 던다** — 큰 면에 채도 최대치 색을 오래 보게 하지 않는다. 대비는 충분하되 눈부시지 않게. 다크 모드. 움직임은 최소
- **가독성** — 본문 16px 하한, 한글 행간, `keep-all`, AA 이상 대비, 위계는 크기보다 굵기·색으로
- **기능이 잘 보이게** — 주요 동작은 찾지 않아도 보이는 곳에. 아이콘만 있는 버튼엔 라벨. 숨은 제스처 금지
- **편안함** — 누르기 쉬운 크기, 되돌릴 수 있게, 결과는 누르기 전에, 막다른 길 없음

## 자연스러운 애니메이션 (본인, 2026-09-26)

> "AI 티는 나지 않으면서 자연스러운 애니메이션과 최대한 UI/UX를 끌어올리고, 어떻게 하면 사용자가 더 편하게 쓰고
> 사이트 구조가 예쁘고 가독성이 좋다고 느낄까를 생각하면서"

**성격 : 치장이 아니라 "부드럽게 이어 주는" 움직임**(본인 보충). 눈에 띄는 효과가 아니라, 화면이 끊기지 않고
자연스럽게 넘어간다고 느끼게 하는 것이 목적이다. 움직임 자체를 알아채지 못해도 성공이다.
"누른 것에만 반응" 규칙을 넓힌다. **이유가 한 문장으로 설명되는 움직임은 넣는다** — 상태가 바뀐 것(선택·해제·필터 적용),
공간의 연속성(시트·다이얼로그가 어디서 나오는지, 목록이 바뀔 때 교차 페이드), 피드백(눌림·저장 완료), 불러오기 → 내용 전환.
- `transform`·`opacity`만 움직인다. 150~300ms, 감속 곡선(토큰), 들어올 때보다 나갈 때를 짧게
- **금지(AI 티)**: 무한 반복 장식, 스크롤할 때마다 튀어 오르는 등장 효과 남발, 패럴랙스, 스크롤 가로채기, 통통 튀는 스프링 과장
- `prefers-reduced-motion`이면 전부 즉시 전환. 레이아웃을 밀어내는 움직임 금지(CLS)

## ⛔ AI스러운 느낌은 아예 배제한다 (본인, 2026-09-26)

`design-taste-frontend` · `ui-ux-pro-max` · `frontend-design` **세 스킬을 모두** 불러와 기준으로 쓴다.

- `design-taste-frontend` 9장(AI Tells)과 14장(Pre-Flight Check)을 **체크리스트로 끝까지 돌린다**
- `ui-ux-pro-max`는 UX 규칙·점검표(`--domain ux`)만 쓴다. `--design-system`이 주는 색·폰트는 쓰지 않는다 — Tailwind 파랑+주황, 한글 없는 폰트라 그 자체가 AI 기본값이다
- 직접 그린 아이콘 금지(Phosphor), 문자 기호(`◐` 등)를 아이콘처럼 쓰지 않는다, 장식용 워터마크 도형 금지, 모든 것을 크게 둥글리지 않는다, Tailwind 기본 팔레트에 가까운 색을 피한다
- 본인이 좋다고 한 요소를 바꿀 때는 **대안과 나란히 비교**해 보여 주고 고르게 한다

세 문서를 함께 쓴다.

| | 담당 |
|---|---|
| `frontend-design` 스킬 | 미감 — 타이포·색·여백, 템플릿처럼 보이지 않기 |

"끝났다"의 정의다.

## UX 5법칙 — 모든 수정 · 개선 · 추가의 기준점 (본인, 2026-10-02)

> "이 기준 스킬들과 효과, 법칙들은 에이전트들이 디자인, UI/UX, 구조, 위치 + 크기, 색깔, 글꼴 등등 모든 구조를 수정 및 개선 및 추가할 때마다 기준점으로 봐야 해(매번 보란 소리)"

**화면 · 컴포넌트 · 스타일을 하나라도 바꾸기 전에 매번** 아래 다섯을 대 본다. 출처 : Laws of UX(Jon Yablonski, lawsofux.com) · Nielsen Norman Group · IxDF — 링크와 원 연구자는 리포 `docs/디자인품질기준.md` "기준 스킬 7개 + UX 5법칙 → 출처". 조사 근거와 우리 화면 적용 사례는 리포 `docs/디자인회의/2026-10-01/00_안건.md` · `README.md`.

| 법칙 | 뜻 | 우리 화면에서 | 잘못 쓰면(하지 않는다) |
|---|---|---|---|
| **힉스의 법칙** (Hick–Hyman) | 선택지의 수 · 복잡도가 늘수록 결정이 느려진다 | 한 순간에 보이는 선택지를 줄인다(필터는 누른 묶음부터) · 추천 · 기본값을 드러낸다 · 기능은 점진적으로 보여 준다 | 단순 결정에만 맞는다 — 사진 피드를 읽고 고르는 일은 대상이 아니다. 줄이다 뜻이 흐려지면 역효과. 결과 고지 · 개인정보 줄은 개수가 아니라 안전이라 줄이지 않는다. 등록 폼을 여러 화면으로 쪼개지 않는다 |
| **피츠의 법칙** (Fitts) | 누르는 시간은 거리와 크기의 함수 — 크고 가까울수록 빠르고 정확하다 | 누르는 면 44px · 사이 8px 이상 · 아이콘만보다 아이콘 + 글자 · 자주 쓰는 동작은 지금 손 · 시선 가까이(제출은 마지막 칸 바로 아래, 휴대폰은 엄지 자리) · **위험 동작은 자주 쓰는 동작과 떨어뜨린다(16px + 모양 차이)** · 확인 버튼이 여는 버튼과 같은 자리에 뜨지 않게 | "전부 크게"가 아니다 — 44px는 누르는 면의 하한(보이는 크기는 `::after`로 넓힘). 화면 가장자리 이점은 마우스만, 터치에서는 가장자리가 오히려 어렵다. 떠 있는 버튼 · 붙는 막대를 늘려 콘텐츠를 가리지 않는다 |
| **제이콥의 법칙** (Jakob Nielsen) | 사람은 대부분의 시간을 다른 서비스에서 보낸다 → 우리도 아는 방식대로 동작하길 기대한다 | **동작과 자리**는 관례를 따른다(뒤로가기 · 주소 공유 · 오류 위치 · 제출 줄 · 상대 시간 · 링크 모양) | **생김새는 따라 하지 않는다** — 관례의 겉모습(하단 탭바 다섯 칸, 흔한 키트 기본 모양)을 들이면 곧 템플릿이 된다(AI 티 배제와 충돌하지 않게). 리포 문서에 외부 서비스 이름을 쓰지 않는다("국내 앱 공통 관례") |
| **근접성의 법칙** (게슈탈트) | 가까이 있는 것은 한 묶음으로 보인다 | **묶음 안 간격 < 묶음 사이 간격**(라벨–칸 4~8px, 묶음 사이 24px 이상) · 관련 동작을 그 대상 바로 옆에(안내 (i)는 설명하는 대상 바로 뒤, 댓글 입구는 댓글 근처) · 긴 폼은 덩어리로 · 모바일로 쌓일 때 관련 요소가 떨어지지 않게 | 근접성은 색 · 모양보다 세다 — 묶음이 **실제 관계**와 맞아야 한다. 관련 버튼을 무관한 버튼 사이에 묻지 않는다. 구분선으로 묶음을 대신하지 않는다(간격으로 가른다) |
| **폰 레스토프 효과** (격리 효과) | 비슷한 것들 사이에서 다른 하나가 가장 잘 기억된다 | 한 화면 · 한 구역의 주 동작 하나만 튀게(색 면 한 묶음 + 잉크 채움 하나) · 필요한 곳에 강조를 준다(연락 입구 · 완료 글 · 방금 틀린 칸) | **강조를 아낀다** — 경쟁하면 아무것도 안 보인다. **색만으로 구분하지 않는다**(글자 · 아이콘 · 모양 같이). 움직임 · 깜빡임으로 강조하지 않는다(`prefers-reduced-motion`). 광고처럼 보이지 않게. 사용자가 칠 수 있는 모양(`!` · `[공지]`)을 시스템 표시로 쓰지 않는다 |

**매번 점검표** — 바꾸는 것마다 결과 보고에 한 줄씩 적는다
1. 힉스 : 이 순간 보이는 선택지가 늘었나 줄었나, 기본값 · 추천이 보이나
2. 피츠 : 누를 곳의 크기 · 사이 간격 · 손에서의 거리, 위험 동작과의 거리
3. 제이콥 : 사용자가 기대하는 자리 · 동작인가(생김새는 우리 것인가)
4. 근접성 : 묶음 안 < 묶음 사이 간격, 관련 요소가 붙어 있나
5. 폰 레스토프 : 이 구역에서 튀는 것이 하나뿐인가, 색 말고 모양으로도 구분되나

법칙끼리, 또는 법칙과 위 원칙(사용자 먼저 · AI 티 배제 · 부드럽게 잇는 모션)이 부딪히면 **사용자 먼저**가 이기고, 판단을 보고에 적는다.

## 제품 성격이 디자인을 결정한다

사용자는 **물건을 잃어버린 직후** 또는 **길에서 뭔가를 주운 직후**에 이 서비스를 연다.
차분히 둘러보는 서비스가 아니다.

- **모바일 우선.** 데스크톱은 넓어진 모바일로 취급한다
- 목록에서 "내 물건인가"를 **1초 안에** 판단할 수 있어야 한다
- 글을 쓰는 사람은 한 손으로, 불안한 상태로 입력한다. 필수 입력을 늘리지 않는다

## 목록은 "의도 우선 + 사진 피드"다 (2026-09-24 재설계)

1차 목록(왼쪽 필터 패널 + 회색 가로형 목록)은 본인이 거부했다 —
**딱딱하고 칙칙함 · 분실/습득 구분이 약함 · 너무 없어 보임.** 데이터 조회 도구처럼 보였다.

- **첫 화면 맨 위에서 의도를 고른다** : `잃어버렸어요` / `주웠어요`. 분실/습득은 필터 하나가 아니라 **서비스 구조**다
- ⚠️ **의도와 보여줄 글은 엇갈린다.** 잃어버린 사람이 알고 싶은 건 "누가 주웠나" → **습득(FOUND) 글**을 보여준다.
  주운 사람에게는 **분실(LOST) 글**. 버튼 아래 한 줄로 **무엇을 보게 되는지**를 적는다
- 목록은 **사진이 큰 격자 피드**(정사각 썸네일, 좁은 화면도 2열). 왼쪽 필터 패널은 없다 — **칩 하나 = 묶음 하나**(2026-10-03 회의 ③) : 카테고리 · 상태는 메뉴에서 누르면 바로 반영되고 닫힌다(화살표는 옮기기만 — WCAG 3.2.2), 장소 · 기간은 한 판 `[지우기]`(보이는 칸만) · `[적용하기]`. 좁은 화면은 작은 바텀 시트, 48rem 이상은 누른 칩 바로 아래 펼침 칸(가로막는 모달 아님). 320은 칩 줄이 줄을 바꾼다
- 목록 넘기기는 모든 폭 **[더 보기]**(`?page` = 펼친 묶음 수, 상한 4 = 96건, 처음부터 한 번에 다시 받기 · 이미 본 카드 제자리 · 96건 너머는 "조건을 좁혀 보세요"). 쪽 번호는 내가 쓴 글에만
- 칩 줄은 헤더 아래 붙는다(높이 40rem · 폭 22.5rem 이상, 검색칸은 붙지 않는다). 글쓰기 입구는 떠 있는 버튼이 아니라 헤더 `[+]`(보던 의도 · 이름을 싣는다)와 흐름 안 링크다
- **사진 없는 글도 초라하지 않게.** 사진은 선택 입력이라 썸네일이 붙어도 빈 글은 계속 나온다.
  회색 네모 대신 유형 색의 연한 바탕 + 큰 카테고리 그림 + 물건 이름으로, 포스터처럼
- 스크린샷을 보고 **"서비스처럼 보이는지"** 를 먼저 판단한다. 기능이 된다고 끝난 게 아니다

## 정보 위계

### 목록 카드

스캔이 목적이다. 눈이 멈추는 순서를 고정한다.

```
1순위   사진(또는 포스터형 자리표시) + 제목
2순위   유형(분실/습득) — 사진 위 배지와 카드의 색 면 · 상태(연락중·완료)
3순위   장소 · 분실습득일
4순위   작성자 닉네임 · 조회수 (피드에서는 줄이거나 뺄 수 있다)
```

본문(`content`)은 목록에 싣지 않는다. 백엔드도 `PostListResponse` 에서 뺐다 —
최대 5000자가 20건이면 10만 자가 나간다.

### 상세

제목 → 이름표 + `댓글 쓰기 N`(연락 입구) → (작성자 본인이면 내 글 관리) → 사진 → 핵심 정보(장소 · 분실습득일 · 종류) → 본문 → 메타(작성자·날짜·조회수) → 댓글 순.
작성자 본인에게만 내 글 관리(상태 · 수정 · 삭제)가 보이고, 제목 바로 아래에 온다(2026-10-03 회의 AR-4).
연락 입구는 셋(배지 줄 · 댓글 제목 옆(댓글 1개 이상) · 휴대폰 하단 줄) — 같은 입구가 동시에 둘 보이지 않게, 누르면 그 이벤트 안에서 입력칸에 포커스(iOS 키보드).

## 배지 체계

두 축을 **색으로 섞지 않는다.** 유형과 상태는 다른 정보다.

| 축 | 값 | 표현 |
|---|---|---|
| 유형 | LOST / FOUND | 채운 배지. 두 색을 확실히 구분 |
| 상태 | OPEN / IN_PROGRESS / DONE | 외곽선 배지 또는 점 + 텍스트 |

⛔ **"색은 유형 배지에만" 규칙은 폐기했다**(2026-09-24). 칙칙함의 원인이었다.
분실·습득 두 색은 **면(surface)** 으로도 쓴다 — 의도 선택, 사진 없는 카드의 바탕, 등록 동선.
색은 **개념에 붙는다** : 분실 색 = 잃어버림(LOST 글, `잃어버렸어요`, 분실 글 올리기), 습득 색 = 주움.

**빨강 = 멈춰서 볼 것**(2026-10-03 회의 ⑤) — 방금 틀린 것(오류 문장 · `!` 아이콘, `--error-text` 밝게 `#A62018` · 어둡게 `#FF8F85`)과 되돌릴 수 없는 동작(삭제). **빨간 채움은 되돌릴 수 없는 확인 버튼만**(`[삭제하기]`). **개인정보 · 경고 · 상태에는 빨강 금지.** 틀린 칸의 테두리는 빨강이 아니라 잉크 두 겹, 오류가 떠 있는 동안 그 칸 도움말은 숨긴다(적색약에게 빨강은 1.74:1뿐 — 지키는 것은 아이콘 · 문장이다).

DONE은 **목록에서 눈에 덜 띄어야 한다.** 이미 끝난 글이다(사진 흑백 + 글자 한 단계 흐림, 반투명 아님). **상세에서는 분명하게** — 같은 잉크 도장 배지 + "주인에게 돌아간 물건이에요." 한 줄(글쓴이에게는 내 글 관리가 한 번만 말한다), 사진은 컬러 그대로.

색만으로 구분하지 않는다. 색각 이상 사용자에게는 배지 두 개가 같은 회색이다.
**항상 텍스트를 함께 둔다.**

## 모든 화면이 가져야 할 네 가지 상태

하나라도 빠지면 화면이 거짓말을 한다.

| 상태 | 규칙 |
|---|---|
| 로딩 | 스피너보다 **스켈레톤**. 레이아웃이 튀지 않는다 |
| 비어 있음 | "조건에 맞는 글이 없어요." 를 화면이 말한다(프론트 문장은 해요체). 빈 화면은 오류처럼 보인다. **검색어 · 주소 값을 제목 문장에 넣지 않는다**(콘텐츠 위조). 회색 판 대신 다음 행동(등록 권유 면) |
| 오류 | 백엔드 `message` 를 **그대로** 보여준다. 전역 예외 처리가 한글 문장을 준다 |
| 권한 | 비로그인에게 수정·삭제 버튼을 **보이지 않게** 한다. 비활성화가 아니라 숨김 |

## 선택의 결과를 먼저, 한 번, 정확하게 알린다

이 서비스의 핵심 UX 규칙이다. 사용자가 누르기 **전에** 그 선택이 무엇을 바꾸는지 알아야 한다.

1. **알리는 시점은 누르기 전.** 누른 뒤 토스트로 알리면 늦다
2. **한 번만 말한다.** 같은 내용을 두 번 묻거나 여러 곳에 반복하지 않는다.
   경고가 반복되면 사용자는 읽지 않고 누르는 법을 배운다
3. **구체적으로.** "정말 삭제하시겠습니까?" 는 아무 정보도 주지 않는다.
   무엇이 함께 사라지는지 숫자로 쓴다

### 동작별로 반드시 알려야 할 결과

| 동작 | 알려야 할 결과 | 형식 |
|---|---|---|
| 게시글 등록 | 사진은 최대 5장 | 인라인 |
| 게시글 수정 | **새 사진을 올리면 기존 사진이 전부 교체된다.** 안 올리면 유지 | 인라인 |
| 게시글 삭제 | 글·첨부 사진·**달린 댓글이 함께 사라진다. 되돌릴 수 없다** | 다이얼로그 |
| 상태 → 완료(DONE) | **되돌릴 수 없다.** 게시중↔연락중은 오갈 수 있지만 완료가 마지막이다 | 다이얼로그 |
| 비밀번호 변경 | **이 기기를 포함해 로그인된 모든 기기에서 로그아웃된다** | 인라인 |
| 닉네임 변경 | 지금까지 쓴 글과 댓글의 이름이 **전부 바뀐다** | 인라인 |

삭제가 댓글까지 지우는 건 `PostService.delete()` 가 `commentRepository.deleteByPostId()` 를
먼저 호출하기 때문이고, 비밀번호 변경이 전 기기를 로그아웃시키는 건
`MemberService.updatePassword()` 가 `refreshTokenService.delete(memberId)` 로 리프레시 토큰을
폐기하기 때문이다. **둘 다 사용자가 예상하지 못하는 결과다. 반드시 알린다.**

### 인라인 / 다이얼로그 구분

되돌릴 수 있으면 **인라인 한 줄**, 되돌릴 수 없으면 **확인 다이얼로그**.

- **인라인** : 버튼이나 입력 바로 아래 한 문장. 작고 흐리게. 진행을 막지 않는다
- **다이얼로그** : 결과를 문장으로 쓴다. "삭제"는 파괴적 색상, **기본 포커스는 "취소"에**. 열린 뒤 **0.5초 안에 시작된**(`pointerdown`) 마우스 · 터치 누름은 확인 버튼 · 바깥 닫기 모두 무시한다(`pressGuard`, SE-1 — 두 번 누름이 막 뜬 확인 버튼에 떨어지지 않게). 키보드 · `[취소]`는 즉시, 버튼 모양은 바꾸지 않는다
- 여는 위험 버튼은 자주 쓰는 버튼과 **16px** 떼고 모양도 다르게(`[수정]`–`[삭제]`). 줄 끝으로 옮기지 않는다 — 확인 버튼 자리와 겹친다

되돌릴 수 있는 일에 다이얼로그를 띄우지 않는다. 규칙 2를 깨는 가장 흔한 방법이다.

### 문구 예시

프론트가 짓는 문장(빈 상태 · 확인 창 · 결과 고지 · 도움말 · 보내기 전 검사 · 연결 실패)은 **해요체**다(2026-10-03 회의 ⑦). 서버가 보내는 `message`(합니다체)는 그대로 둔다 — 바꾸려면 백엔드 `ErrorCode`. 보내기 전 검사 문장도 **칸 이름으로 시작**한다(서버 문장 첫 낱말로 칸을 가리는 규칙 — `이메일` · `비밀번호` · `닉네임`). 부정문보다 긍정문, 문구 안에 `↓` `→` `✓` 같은 글자 기호를 아이콘처럼 쓰지 않는다(Phosphor 아이콘으로).

```
✗  정말 삭제하시겠습니까?
✓  이 게시글을 삭제하면 사진 3장과 댓글 5개가 함께 사라져요.
   되돌릴 수 없어요.

✗  비밀번호가 변경되었습니다.
✓  비밀번호를 바꾸면 이 기기를 포함해 로그인된 모든 기기에서 로그아웃돼요.

✗  새 사진을 올리면 기존 사진 2장은 삭제됩니다. 그대로 두려면 선택하지 마세요.
✓  지금 사진 2장이 그대로 남아요. ‘새 사진으로 바꾸기’를 고르면 2장이 모두 바뀌어요.

✗  완료로 변경하시겠습니까?
✓  완료로 바꾸면 다시 게시중이나 연락중으로 되돌릴 수 없어요.

✗  댓글 내용은 필수입니다     (서버 문장을 따라 쓴 보내기 전 검사)
✓  댓글을 적어 주세요
```

## 백엔드에 없는 기능은 화면을 만들지 않는다

2026-09-22 확인 기준, 회원 관련 엔드포인트는 셋뿐이다.

| | |
|---|---|
| `GET /api/members/me` | 내 정보 조회 |
| `PATCH /api/members/me` | **닉네임만** |
| `PATCH /api/members/me/password` | 비밀번호 |

⛔ **이메일 변경과 프로필 사진은 백엔드에 없다.** MEMBER 테이블에 프로필 이미지 컬럼
자체가 없다(`member_id`, `email`, `password`, `nickname`, `created_at`, `updated_at`).
화면에 넣으면 눌러도 아무 일도 안 일어나는 버튼이 생긴다.

필요하면 백엔드 작업(엔드포인트 + Flyway 마이그레이션 + S3 연동)이 선행되어야 한다.
**임의로 만들지 말고 보고한다.**

## 폼

- 검증은 **제출 시점**이 아니라 필드를 벗어날 때. 제출 후에야 다섯 개가 한꺼번에 빨개지면 늦다
- 서버 검증 메시지(`message`)를 해당 필드 아래에 붙인다. 상단 배너로 몰지 않는다
- 오류는 `!` 아이콘 + 문장(`--error-text`), 칸 테두리는 잉크 두 겹. 오류가 떠 있는 동안 도움말은 숨기고 결과 고지 줄은 남긴다
- **알림은 한 번만** — 벗어나며 생긴 오류 하나만 바로 읽고, 제출이 막히면 첫 틀린 칸으로 포커스 + 제출 줄 위 "3곳을 더 채워야 올라가요" 한 줄(칸마다 `role="alert"`를 울리지 않는다)
- 예시는 입력칸 안 안내 글(이름은 늘 위), 글자 수는 한도의 80%부터, 당연한 도움말은 뺀다
- **전송 중에는 제출·취소 버튼을 잠근다.** 이미지 5장이면 몇 초 걸리고, 그 사이 중복 클릭이
  들어가면 게시글이 두 개 만들어진다. 취소를 눌러도 이미 서버에 닿은 요청은 처리된다
- 작성 중 이탈은 **쓰던 칸 등록부**(`shared/lib/dirtyRegistry`) 하나로 확인한다 — `useBlocker`는 한 번에 하나라 막는 곳은 레이아웃에 하나, 칸은 "쓰던 글자 있음"만 알린다(`useDirtyField`). 로그아웃 확인(쓰던 글자가 있을 때만) · 다른 창 로그아웃(쓰던 글자를 읽기 전용으로 남기고 저장소에 넣지 않음)도 같은 판정을 읽는다
- 쓰는 칸(제목 · 장소 · 설명 · 댓글)에 전화번호 · 주민번호 · 카드 번호 모양이 보이면 **그때만** 한 줄(입력 0.6초 멈춤 + 칸 벗어날 때, 막지 않음, 빨강 아님). 줄이 생겨 제출 버튼이 밀리지 않게 자리를 비우거나 버튼 줄 왼쪽에 둔다

## 이미지

- 게시글당 **최대 5장**. 6장째를 고른 순간 UI에서 막는다. 서버까지 보내고 400을 받지 않는다
- 이미지가 없는 글이 많다. **플레이스홀더를 성의 있게** 만든다. 작은 아이콘 하나로는 부족하다 —
  유형 색 바탕 + 큰 카테고리 그림 + 카테고리 이름으로 **의도한 디자인처럼** 보여야 한다
- 목록 썸네일은 고정 비율로 자른다. 세로 사진 때문에 카드 높이가 들쭉날쭉하면 스캔이 안 된다
- `alt` 는 "이미지" 가 아니라 게시글 제목을 쓴다

## 선택 표시 · 붙는 것 (2026-10-03 회의)

- **선택 표시** : 하나만 고르기 = 채운 점 · 여러 개 고르기 = 네모 체크 · 그림 칸(종류 · 화면 모드) = 선 두 겹 + 접힌 귀퉁이 · 탭 = 밑줄 · 의도 = 색 면 + `[×]`. **동그라미 ✓는 "완료" 표시 전용**이라 선택에 쓰지 않는다. 화면 모드는 기기 설정을 따르는 중이면 빈 테 귀퉁이 + `기기 설정` 이름표, 고정하면 채운 귀퉁이
- **붙는 것 총량** : 한 화면에 붙는 것은 **헤더 + 줄 하나까지**. 둘째 줄은 `min-height: 40rem`에서만, 떠 있는 버튼도 하나로 센다(그래서 두지 않는다). 목록 = 칩 줄 · 상세 = 휴대폰 댓글 줄 · 폼 = 휴대폰 제출 줄(40rem 미만은 폼 끝 제자리). 짧은 알림은 아래 붙은 줄 위로 비켜 뜬다(`--bottom-inset`)
- **헤더** : 로그인하면 톱니 없이 계정 메뉴의 "설정" 하나, 비로그인은 톱니 + 글자 버튼 `[로그인]`. 누르는 면끼리 8px. 로그인 · 가입 화면에서는 `[로그인]`을 숨기되 자리는 남긴다. 어둡게 주 버튼은 `#D5D8DD`(글자색보다 한 단계 낮춰 눈부시지 않게)

## 접근성 최소선

- 모든 폼 입력에 `label`
- 배지·상태를 색만으로 구분하지 않는다
- **320px**에서 가로 스크롤이 생기지 않는다(폴드 접힘). 375만 보면 놓친다
- 375 / 768 / 1440 에서 각각 실제로 렌더링해 본다. 브라우저 확대 200%도
- 터치 대상 최소 44×44
- 포커스 링을 지우지 않는다

## 이 화면들은 포트폴리오에 실린다

이 프로젝트는 백엔드 포트폴리오이고, 프론트는 **"찍을 화면이 없다"는 약점을 메우는 수단**이다.
기능만 되는 회색 화면은 목적을 절반만 달성한 것이다. 스크린샷 한 장으로 판단된다는 전제로
만든다.

검증하다 상태를 만들었으면 **그 자리에서 스크린샷을 남긴다.** 나중에 재현하려면 조건을
다시 만들어야 하는 것들이 있다(예: 로그인 5회 실패 423 화면).
